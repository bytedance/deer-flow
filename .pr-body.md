## Why

DeerFlow's research loop fans out into a lot of searches per task, so the `web_search` slot matters more here than in a chat wrapper. Every keyed engine in the picker (Tavily, Exa, Firecrawl, fastCRW, Brave, GroundRoute, InfoQuest) makes a new user stop and go get a key before they can run anything, and the one zero-config option — DuckDuckGo — is a scraped aggregator, not an API.

You.com fills that gap: it has a free tier that needs no key at all, and the same provider upgrades to the full Search API when the operator sets one. So `make setup` can hand someone a real search API on the first run, and nothing has to change when they outgrow the free tier.

The result shape also suits a long-horizon harness. You.com returns extracted page snippets per hit — several passages from the page body — rather than a single meta description, so the agent gets usable context without spending a `web_fetch` on it.

## What changed

A new opt-in community engine, `deerflow.community.youcom`, providing `web_search`. Nothing changes for existing users: no default is touched, no new dependency, no `uv.lock` churn.

Picking it in `make setup` requires no API key. The provider chooses its endpoint by whether a key is configured:

| | Endpoint | Auth |
|---|---|---|
| No key | `https://api.you.com/v1/agents/search` | none — free tier, currently 100 searches/day |
| `YDC_API_KEY` set | `https://api.you.com/v1/search` | `X-API-Key` — full Search API, higher limits |

The key is read from the tool's `api_key` config first, then the `YDC_API_KEY` env var — the same resolution order as brave/groundroute/exa. Endpoint and headers are always selected together, because the keyless endpoint rejects an auth header and a stale key must never reach it; there's a test pinning that.

Both endpoints return the same body, so one normalizer covers both. `web_search` returns a JSON list of `{title, url, snippet}`, where `snippet` is the joined `snippets` array and falls back to `description` for news hits, which don't carry one.

One detail worth flagging for review: You.com applies `count` **per section**, so a `count=5` request can come back with 5 web + 5 news results. The merged list is web-first and trimmed back to `count`, so `max_results` keeps meaning what it means for every other engine.

Scoped to `web_search` deliberately. No `web_fetch` — Jina AI, Crawl4AI, and Browserless already cover that.

Files:

- `backend/packages/harness/deerflow/community/youcom/{tools.py,__init__.py}` — the provider (httpx only; httpx is already core, so no extra and no lock change).
- `scripts/wizard/providers.py` — `SEARCH_PROVIDERS` entry, appended so existing wizard-test indices don't shift. `env_var=None` because the wizard shouldn't demand a key the provider doesn't need.
- `scripts/doctor.py` — registered under `free_providers["web_search"]` so `make doctor` reports it correctly without a key.
- `config.example.yaml` — commented `web_search` stanza.
- Docs: `backend/docs/CONFIGURATION.md`, `frontend/src/content/{en,zh}/harness/tools.mdx`, and the provider list in `backend/packages/harness/deerflow/tools/AGENTS.md`.
- `backend/tests/test_youcom_tools.py` — 24 tests.

Requests to You.com send a `User-Agent` identifying DeerFlow (`deerflow-harness/<version> youdotcom-integration/bytedance-deer-flow`) so You.com can attribute integration traffic. It's the only attribution signal available on the keyless tier, since there's no key to tie usage to. It goes to You.com hosts only — this module makes no other calls — and a test pins the format. Happy to drop it if you'd rather providers stayed anonymous.
