# DeerFlow checkpoint 轨迹插件

版本 `0.6.2`，适配官方 DeerFlow `2.3.0-dev`（本地验证基线 `2cc30714c`）及 extension-api `0.2.13`。

从对话菜单打开轨迹页时，插件会自动识别当前对话。可以查看已保存的运行步骤、压缩前后对照以及模型和工具耗时，定位慢步骤、工具失败和重试线索，并导出 JSON 或 Markdown＋图片 ZIP。

**安装或升级**时，在 DeerFlow 的 `backend` 目录运行下面的命令。首次安装将 `upgrade` 换为 `install`。

```bash
uv run deerflow extensions upgrade ../examples/deerflow-extension-trajectory --yes
```

Docker 部署须在实际运行 Gateway 的环境中同步插件。

**持久化子执行标识和历史**时，在宿主 `config.yaml` 的对应配置段中使用文件型 SQLite，并开启 `subagent_runtime.checkpoint_enabled`。已有 SQLite 配置时沿用现有数据目录。

```yaml
database:
  backend: sqlite
subagent_runtime:
  checkpoint_enabled: true
```

宿主为每次普通 `task` 委派自动生成子执行标识。开启持久化后，宿主将这个标识、与父 `task` 调用的关联及子步骤写入 checkpoint。轨迹页据此区分并行子任务，把各自的模型调用、工具调用和结果放在对应的父调用之后。Gateway 重启后也能读取已保存的子轨迹。

安装并启用插件、完成所需配置后重启 Gateway，再从对话菜单选择“运行轨迹 → 查看本对话轨迹”。

## 数据来源与配置

轨迹沿当前分支已保存的 checkpoint 父链读取，逐对比较父快照和子快照，显示新增或更新的用户消息、助手消息、工具调用参数、工具结果和错误状态。工具名称保留原始名称。

`run_events.backend` 可以保持 `memory`，本插件不读取 run events。要跨重启保留轨迹，宿主的 checkpoint 数据库仍须持久化（例如 `database.backend: sqlite`），Docker 的数据目录也须持久化。切换事件后端不会补回已丢失的 checkpoint，也不会删除以前写入数据库的 run events。

轨迹的历史范围取决于当前分支仍保留的快照。消息列表时间是快照保存时间，独立计时记录的时间是调用结束时间。耗时来自实际计时。历史被清理时显示缺失提示。普通轨迹卡片中的消息文本和每项工具参数最多显示 4000 字符。

## 浏览轨迹

初次打开或点击“最新一轮”时，从最新快照向前分批读取，直到找到最后一次可见用户提问，只显示该轮已保存的轨迹。“加载更早记录”每次在已有内容前补充前一轮；同一批顺带读到的更早记录会缓存，暂不显示。“读取整个对话”继续读取所有剩余轮次，读取期间可暂停。点击“最新一轮”会清空页面缓存，重新读取最新状态。

页面采用浅色分隔的时间线布局：用户的图标和名称为蓝色，助手的机器人图标和名称为绿色，工具的扳手图标和名称为琥珀色；历史读取按钮使用描边样式，导出位于标题右侧。耗时定位与失败/重试面板并排显示，窄屏自动上下排列；支持宿主的浅色和深色主题。

页面按父链顺序从早到晚展示已加载轮次，每页最多渲染 100 条，轮次标题在记录框外且可折叠；记录默认单行，点击展开内容。日期时间在详情第一行，列表右侧显示已记录的耗时。“轮次”按可见用户提问划分，不代表内部 run 的精确起止，也不保证当前轮已运行结束；未读完历史时使用“最新一轮／倒数第 N 轮”，全部读完后才显示正序编号。若历史起点缺失，仅显示仍保存的片段及缺失提示。它只跟随当前分支父链，不把其他分支混进来。

## 子 agent 轨迹

子 agent 的指令、助手消息、内部工具参数和工具结果直接列在主轨迹外层，放在对应 `task` 调用之后，不需要展开父调用。每条子记录可独立展开，并标明子 agent 名称；分段标题区分子执行；内部保留执行 ID 与所属委派 ID，页面不显示这些标识。主子记录共同分页，每页最多 100 项，每条记录保留独立的来源标识，方便定位错误。同时发起的子任务按委派关系分段展示，不按时间戳强行合成一个全局执行顺序。

页面自动读取当前页所涉及的子轨迹，同时最多发起两个子记录请求。较长的子历史可继续“加载更早子步骤”；读取失败可单独重试。“最新一轮”会重新读取最新的子历史，并忽略刷新前尚未返回的结果。无可读取的子历史时显示缺失说明，不把主任务返回的汇总当作内部步骤。

关联使用外层工具调用 ID、发起调用的助手消息 ID 和保存的 checkpoint 父链，并保留子记录中的父 run ID、真实 namespace 与 execution ID。父快照不必额外保存 run ID；同一轮或不同轮次复用调用 ID也不会合并。页面不按主子快照的时间戳强行合成一个全局执行顺序。子数据沿用线程所有权与存在性检查，签名分页标记绑定用户、线程和选定子执行。读取也兼容 full/delta；delta 消息经过状态访问器还原。

查找每次最多扫描 2000 个候选 checkpoint、列出 64 段子历史，并最多校验 1000 个父链节点；达到上限会提示列表可能不完整。打开一段子历史时，页面自动读取最多约 1000 个快照或 200 条记录，之后可继续手动加载。请求沿用 20 秒和两路并发限制。

JSON 导出的 `tool_calls[].subagents` 保存对应子执行的来源引用及完整可见记录；Markdown ZIP 将子步骤放在对应委派下面。主子记录共用 10000 个快照、50000 条记录和 32 MB 文本预算。导出不受页面的 4000 字符显示限制。普通 `task` 以外的批处理、未启用持久化时的旧任务，以及已清理的子 checkpoint 均不能凭空补回。

## 压缩

展开“压缩”记录时，插件按需读取相邻两份 checkpoint。左侧显示此前的摘要和本次移出的可见消息，包括工具调用参数和结果。右侧显示新摘要，并可展开查看压缩后保留的消息。桌面并排展示，窄屏上下排列。

压缩前的原文从旧快照读取，对照可以展示超过普通卡片 4000 字符限制的内容。含图片等富媒体的消息按保存的内容块显示为结构化 JSON。对照沿用系统和隐藏消息的可见性规则，并注明省略的条数。从消息列表移出的内容可能仍保留在新摘要里。对照只描述保存状态的变化，无法还原完整模型请求或逐条确定原消息如何归入摘要。

读取对照沿用线程权限检查，使用绑定用户和线程的签名标记。单次请求含排队限时 20 秒，JSON 上限为 8 MiB。快照被清理时会报错，超过上限时会提示改用导出。JSON 和 Markdown 导出包含相同的前后对照数据，并受各自的导出上限约束。

自动压缩和手动压缩统一显示为“压缩”。自动压缩依据摘要变化和 `Summarization` 节点证据。手动压缩依据 `source=update`、`manual_compaction` 节点标记、可见消息被移除且数量减少，以及摘要更新为非空内容。

节点标记可能随快照继承，其他程序写出相同特征也可能被归为压缩。插件按快照差异分类，判断结果只说明观察到了哪些变化。只有消息删除或摘要修改、且缺少其他压缩证据时，显示“状态变化”。如果消息和摘要都没变，继承的节点标记不会产生新记录。

## 步骤耗时与定位

安装或升级并重启 Gateway 后，插件通过宿主中间件接口采集主 agent 和子 agent 的模型完整响应耗时、各次工具调用耗时。使用单调时钟；模型计时覆盖一次逻辑调用直到完整响应结束，包含宿主重试、等待与全部流式输出，不是首 token 延迟。工具计时覆盖调用及宿主处理，各次并行调用独立测量；页面不把它们相加当作整轮耗时。

展示子步骤及其计时需要开启文档开头的子 agent checkpoint 持久化。缺少持久化子执行标识时，不把子调用的异常冒充成主 agent 的步骤；外层 `task` 调用自身仍可独立计时。

每条助手或工具记录显示实测耗时，旧记录缺少证据时显示“未记录”，不使用 checkpoint 时间差估算。失败、超时、取消同样记录；未产生完整输出时显示单独的“计时记录”，不会伪造模型或工具输出。强制终止进程、机器断电等使采集回调无法完成的情况不能得到完整耗时。

所有记录的日期时间放在展开后详情的第一行；有耗时说明时合并到同一行。子执行与所属委派信息保留在内部数据中，不显示在详情。助手、工具及独立计时记录的列表右侧继续显示耗时。

打开“耗时定位”可以按耗时降序查看当前已加载步骤，分别筛选超过阈值的步骤和失败/超时步骤，点击“定位”会翻到对应页面、展开并高亮记录。慢和异常是独立属性；正常完成的研究任务可以耗时较长。

“耗时定位”默认显示前五条，“工具失败与重试”默认显示前六条，可在各自的列表内滚动查看其余已加载结果。翻页控件位于轨迹列表底部。

在“耗时定位 → 设置慢阈值”可分别为模型和工具输入秒数（s）。留空沿用框内显示的宿主默认值，宿主未设置该类型的默认阈值时显示“默认无限制”。管理员设置的专属阈值优先。保存后当前浏览器立即用新值判断已加载和后续读取的步骤，导出也应用同样的设置。

慢阈值默认未配置，此时仍可排序定位，但不自动标记“慢”。管理员可在 `config.yaml` 的轨迹插件条目中配置宿主默认值；下列数值仅是配置示例，按实际工作负载调整，修改后重启 Gateway：

```yaml
plugins:
  - use: deerflow_extension_trajectory:install
    config:
      timing:
        enabled: true
        slow_thresholds_ms:
          model: 60000
          tool: 30000
          tool:bash: 60000
          tool:task: null  # 此工具不按全局工具阈值标慢
```

支持 `model:<配置名称>` 与 `tool:<工具名称>` 覆盖对应类型的默认阈值；`null` 明确禁用该项慢标记。阈值仅影响展示和筛选，修改后也适用于已有实测记录，不会中止工具或改变模型运行超时。

计时同时写入消息 metadata 和插件自己的 `{DEER_FLOW_HOME}/extensions/trajectory/timings.sqlite`（缺省在宿主 `.deer-flow` 内）。独立记录让未写入消息 checkpoint 的异常仍能在重启后查阅；它只保存身份、关联、时间和状态，不保存提示词、工具参数、正文或凭据。读取沿用线程权限；失败记录按保存的 checkpoint 分支关联。JSON 和 Markdown 导出包含同样的计时证据。`timing.enabled: false` 停止新采集，已有记录仍可读。

宿主返回带 `deerflow_error_fallback` 标记的助手提示时，轨迹显示模型失败。已有实测耗时继续显示，缺少计时的旧消息显示“未记录”。

## 工具失败与重试定位

“工具失败与重试”面板汇总当前已加载的主子步骤。插件依据宿主保存的工具状态和插件记录的失败、超时计时定位问题。没有计时的旧记录仍可按工具状态定位。仅有 `Error:` 开头的正文，或该正文与成功状态冲突时，会列为“待核对”。`glob` 搜索无匹配是正常结果。

`bash` 工具详情照常显示正文。正文中的 `Exit Code:` 属于工具输出，宿主可以用它推断工具状态。只有快照已经独立保存了进程退出码时，详情才会显示具体值，否则显示“未记录”。

同一轮、同一执行中，前一次失败结果已保存后再次发起相同工具与完整参数的调用，列为“失败后相同调用”。与失败调用访问同一条字面绝对路径的后续操作（包括换工具）只列为“可能重试”；这是一条带置信类别的推断，不证明模型意图。并行发起、尚未收到失败结果的调用不会互相算成重试；新用户轮次和不同子执行互相隔离。路径仅从有限的结构化文件参数或 shell 字面 token 提取，不执行 shell、不读取文件来推断关系。

点击面板条目会切到对应页、展开所属轮次和记录并高亮定位。面板默认显示前六条，可在列表内滚动查看其余结果。JSON 和 Markdown 导出保留失败依据、重试线索、调用与结果的关联、同轮同执行内相同调用的次数，以及定位原始记录所需的标识。只有 checkpoint 里可核实的重试才计入次数。

## 兼容性与性能

右上角“导出轨迹”提供 JSON 和“Markdown＋图片 ZIP”。点击后后端独立读取当前分支的完整可用父链，无须先点击“读取整个对话”；读取起点固定为导出开始时的最新 checkpoint。导出包含完整消息文本、工具参数与结果，不受页面 4000 字符截断影响。JSON 包含结构化记录、图片路径和历史完整性说明，不嵌入图片字节。ZIP 包含 `trajectory.md`、`images/` 和 `EXPORT_NOTES.txt`，解压后保留目录结构即可在支持 Markdown 图片的阅读器中查看。

导出沿用线程读取权限，图片从当前用户、当前对话的上传目录读取，拒绝路径越界与符号链接。仅打包插件已识别的上传图片；缺失或不支持的文件在说明中列出。图片为导出时的文件版本，不能保证与历史调用时字节一致。导出不调用模型，不修改 checkpoint，不另存轨迹数据库；生成后由浏览器下载。宿主内部状态读取接口与图片路径布局仍是版本兼容依赖。

每个 Gateway 进程最多同时执行一个导出，含排队限时 120 秒；最多扫描 10000 个快照、50000 条记录，投影文本 JSON 累计不超过 32 MB。ZIP 最多 200 个不同图片路径、单图 20 MB、去重后的图片总量 64 MB，超过限制会报错而不下载截断文件。文本整理、数据库读取及图片打包仍有 CPU、内存和 I/O 开销；图片打包放在工作线程，不在每次模型调用中执行。异常或超时后的工作线程会结束后再释放导出名额。

页面隐藏没有可展示文字、图片、工具调用或状态信息的空记录，也不显示“更新”标签；原始消息仍参与轮次划分，图片和纯工具调用不会因没有文字被隐藏。

上传图片预览：从用户消息的 `current_uploads` / `uploaded_files` 记录中提取上传目录内的 PNG、JPEG、WebP、GIF 引用，每条最多 16 张。展开记录时通过宿主的带对话权限检查的 artifacts 接口加载，显示缩略图并支持点击放大；原始上传说明保留在“上传文件说明”中。图片只在浏览器页面内缓存，退出时释放，不另存数据库。单张预览限制 20 MB，文件丢失或无权访问时显示失败提示并可重试。尚不覆盖没有上传记录的图片内容块、外部图片地址或工具生成图片；路径引用不保证原文件永久存在。

公开 extension-api 目前没有 checkpoint reader；`gateway.py` 集中适配宿主的 `require_permission` 与 `build_thread_checkpoint_state_accessor`。这是对当前宿主内部接口的依赖，升级 DeerFlow 后需要重新验证。读取使用宿主的状态还原接口，兼容其 full/delta 通道处理；不直接把原始 delta 数据当成完整消息。

每次请求先检查登录、线程访问权限及线程存在性；分页标记绑定用户和线程并签名。删除线程后不能通过旧分页标记继续读。Gateway 重启会使旧分页标记失效，刷新页面重新读取即可，磁盘上的 checkpoint 不受影响。

消息轨迹仍按需读取 checkpoint。启用计时后，每次模型或工具调用会额外写入一条轻量计时证据；文件操作放到线程执行，计时写入本身不计入显示的调用耗时。不采集隐藏推理或完整模型输入。打开页面时，读取仍会与推理共享 CPU 和数据库。每批最多 24 个快照，读取一轮可能需要连续请求多批；最多两个并发读取请求，单次请求含排队限时 20 秒。服务端只保留相邻快照，浏览器缓存已读投影；刷新后重新读。单次连续读取达到 10000 个快照，或全量读取累计达到 10000 条已展示记录时暂停，可手动继续。超大单个快照及 delta 还原仍可能较慢，不能保证所有负载都无影响。

## 本地验证

安装仓库依赖后，从仓库根目录运行以下命令验证插件和浏览器模块。

```bash
PYTHONPATH=backend:examples/deerflow-extension-trajectory backend/.venv/bin/python -m pytest examples/deerflow-extension-trajectory/tests -q
node --test examples/deerflow-extension-trajectory/tests/test_turns.mjs
```

首次运行端到端测试时，先在 `frontend/` 运行 `pnpm exec playwright install chromium`。随后在同一目录运行 `pnpm exec playwright test tests/e2e/trajectory-plugin.spec.ts --workers=1`。

CI 在隔离环境中安装 wheel 并验证插件，也用 Chromium 和临时测试 Gateway 验证轨迹浏览和导出。 [安装包验证](../../.github/workflows/trajectory-plugin-tests.yml) · [浏览器验证](../../.github/workflows/e2e-tests.yml)
