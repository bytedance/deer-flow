### 各键影响什么

- `database.checkpoint_channel_mode` 决定 `messages` 通道的存储形态：整份取值（`full`）还是 LangGraph `DeltaChannel` 哨兵加逐步写入（`delta`）。它影响一个线程的每一次读写。
- `database.checkpoint_delta.snapshot_frequency` 是 delta 模式下每 N 次逐步写入落一份完整 messages 快照的节奏。值越大检查点越小、物化越慢。`full` 模式下被忽略。
- `database.checkpoint_graph_cache.accessor_graph_max` 限制进程缓存的已编译线程状态访问器图数量，键按 assistant、通道模式与快照节奏组合。与模式和节奏不同，它不需要重启：容量不同只会改变缓存何时淘汰，不会改变图的语义。
- `database.checkpoint_cache.*` 只配置 delta 模式下的物化历史缓存。它纯属性能优化、永不冻结——没有任何正确性不变量要求跨进程一致，禁用缓存时结果也完全相同——但它**不是热重载**：缓存对象在启动时随 checkpointer 一起构造（`deps:463`、`asyncprov:250-254`），而 `reload` 把整个 `database` 段登记为 startup-only（`reload:47`），所以改动其中任何一项都需要重启。memory 后端受 `max_entries` 约束，redis 后端受 `ttl_seconds` 与服务器自身 maxmemory 策略约束。
- `database.backend` 决定由哪种 saver 承载线程（`InMemorySaver`、SQLite 或 Postgres）。模式语义位于已编译的通道表而不是 saver，所以三种后端都支持两种模式。

两个冻结键的 `Field(description=...)` 原文值得读一遍，因为它写明了跨进程规则：

```text
"Checkpoint representation for accumulating channels. 'full' preserves full-value message checkpoints;
'delta' uses LangGraph DeltaChannel for messages. Restart is required, and all processes sharing one
checkpoint database must use the same value."
```

```text
"DeltaChannel snapshot cadence: a full messages snapshot is stored every N per-step writes
(higher = smaller checkpoints, slower materialization). Restart is required, and all processes
sharing one checkpoint database must use the same value."
```

旧的顶层键 `database.checkpoint_delta_snapshot_frequency` 仍被 pydantic 的 `@model_validator(mode="before")`（名为 `_migrate_legacy_snapshot_frequency`）接受。它只会记录以下三条字符串之一，全部对运维可见：

### 环境变量

没有任何环境变量能选择检查点模式或快照节奏，两者只来自 `config.yaml`。本特性唯一相关的环境变量是历史缓存 redis URL 的回退链（`DEER_FLOW_CHECKPOINT_CACHE_REDIS_URL`、`REDIS_URL`、`redis://localhost:6379/0`），见 `cacheprov:19-23`。配置值里的 `$VAR` 插值由 `AppConfig.resolve_env_variables()` 在构造 `DatabaseConfig` 之前统一处理，因此 `DatabaseConfig` 自身不做任何环境处理（`dbcfg:13-22`、`appcfg:442`）。

### 配置版本

该 schema 变更随 `config_version 27` 发布；`config.example.yaml` 当前是 `config_version: 49`，缺少版本号按 `0` 处理（`example:23`、`appcfg:531-575`）。过旧的 `config.yaml` 会记录：

```text
Your config.yaml (version %d) is outdated — the latest version is %d. Run `make config-upgrade` to merge new fields into your config.
```

`make config-upgrade` 会以安全默认值 `full` 合并新键（`appcfg:570-575`、`backend/tests/test_config_version.py:151-203`）。通用升级流程见[配置](/docs/harness/configuration)。

### HTTP 状态映射

只有 threads 路由导入这些异常。它注册门禁元组 `_CHECKPOINT_MODE_ERRORS = (CheckpointModeMismatchError, CheckpointModeReconfigurationError)`（`threads:82`），映射如下。响应体是 FastAPI 默认的 `{"detail": "<string>"}`。

| 条件 | 状态码 | `detail` | 证据 |
| --- | --- | --- | --- |
| `CheckpointModeMismatchError` | `409` | `f"Thread {thread_id}: {exc}"`，即 `Thread <thread_id>: Thread requires delta mode; materialize and convert its checkpoints before using full mode.` | `threads:105-106` |
| `CheckpointModeReconfigurationError` | `503` | `str(exc)` | `threads:107` |

路由给出的理由：不匹配说明线程持久化的检查点与进程冻结的模式冲突（运维可处理，409）；重新配置说明进程自身正处于模式切换中（暂时性，503）（`threads:99-102`）。`503` 这一半属于防御性代码 —— 这些路由中没有任何路径会抛出它。冻结辅助函数只被 Gateway 启动（`deps:451-452`）、`agent:835,839` 与 `client:230-231` 调用，而没有任何状态、历史或线程路由会构建 agent：`checkpoint_channel_mode` 的改动会被 run worker 注入的值覆盖（`worker:1018-1019`，优先采用于 `agent:831-835`），在重启前被忽略；`snapshot_frequency` 的改动则会让下一次 run 失败（`worker:1450-1462`），而不是返回某个状态码。
