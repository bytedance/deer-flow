## 1. 先从用户要的结果推导，而不是从 Fleet 组件推导

用户给出目标后，可以离开页面。系统按任务需要使用已有 ECS，能够查看进度、取消、取得文件，必要时等待外部计算后继续原目标。短交互仍可本地执行，重任务自动选机；同一机器池既执行程序，也执行完整 Agent。

由此产生五类责任：

1. 理解目标、调用模型和工具：Agent 运行时。
2. 保存会话、目标、执行结果：持久状态。
3. 决定哪里执行、什么时候执行：资源调度。
4. 让程序或 Agent 在目标机器实际运行：执行后端。
5. 把异步结果交还原会话并继续目标：任务衔接。

DeerFlow 已实现第一类、第二类和第五类的一部分。新增内容应主要落在第三类、第四类和第五类的缺口。网络、容器、Jenkins、NAS 是实现条件，不能反过来要求重新实现整个 Agent 系统。

B 是不需要模型参与的持久程序任务；C 是完整 Agent 在工作机执行。两者并存。C 在工作机执行，并不自动意味着要新写一套 Agent runner；运行原生 Gateway 实例也是一种实现路径。

## 2. 原生与新增的逐项边界

| 需要的功能 | 原生已经提供 | 本次应如何实现 |
|---|---|---|
| 模型、规划、工具、多轮推理 | lead Agent、run_agent、中间件与工具体系 | 完整复用，远程节点也运行相同原生生命周期 |
| 会话、用户鉴权、历史、文件入口、SSE | Gateway、Thread/Run、授权和事件接口 | 复用入口，新增任务信息作为关联展示 |
| checkpoint 和持久 run 状态 | PostgreSQL checkpointer、runs、run events | 复用，不建立平行 checkpoint 系统 |
| 一个目标多轮继续 | 原生 GoalState、目标评估与续跑预算 | 原生 goal 是目标语义的优先来源；外部依赖等待增加关联信息 |
| 长任务持久跟踪、状态查询、取消、重启后继续轮询 | McpTaskService、mcp_tasks、普通 MCP submit/status/cancel 适配 | B 接入原生任务机制；不在 Agent 提示词里维护长期轮询循环 |
| 外部任务完成后唤起 Agent | 原生幂等 MCP notification run | 优先复用；补充目标仍有效、用户取消、依赖集已满足等约束 |
| 批量子 Agent、排队和并发上限 | task、batch_task、持久 batch service | 复用；它们目前仍在所属 Gateway 的进程中执行，不冒充跨 ECS 调度 |
| 定时执行和忙时持久排队 | 原生 Scheduler | 复用触发与 occurrence 队列；不能把它当作任意资源任务的通用执行队列 |
| bash/Python 隔离与远程 sandbox | SandboxProvider、AIO、远程 provisioner 等 | 优先复用 provider；普通固定 ECS 池的创建/选机适配仍需核对与补齐 |
| 多实例 run ownership、跨实例取消、事件传输 | run_ownership、持久取消、Redis stream bridge、multi_instance 配置门槛 | 作为 C 的基础，不能继续描述成原生完全没有分布式运行协调 |
| 固定 ECS 注册、健康、排空、自动选机 | 不等同于原生多 Gateway 支持 | 新增小范围节点管理与调度适配 |
| B/C 共用 CPU、内存、并发预算和资源排队 | 原生各子系统限流不等于机器池统一资源账 | 新增共享资源准入；空闲 CPU 百分比不能代替资源预留 |
| 程序任务实际容器执行与退出确认 | Sandbox 有生命周期能力，但普通同步工具不等于持久 B 执行服务 | 持久执行后端负责；优先适配已有能力，确有缺口再实现 |
| 完整 Agent 远程执行 C | 原生完整运行时可以部署在另一实例；不自带本需求的自动 placement | 复用运行时与存储，补充队列、选机和可信启动衔接 |
| C 等待 B、释放容量、结果到达后继续同一目标 | Goal 与 MCP notification 各自已有部分能力 | 新增窄范围依赖协调；不得直接宣称两者配置一起就完整支持 |
| NAS 跨机共享文件 | 既有 thread/user 路径与文件授权可复用 | 统一挂载和身份；必要的输出提交、并发写隔离要保留 |
| Jenkins 发布、停止、重启、版本回退 | 已有 Docker/Compose 构建启动基础 | 最后做部署编排；不把运维流程扩张成另一套执行框架 |

## 3. 需要纠正上一轮的两个关键结论

### 3.1 C 不必天然等于自建完整 runner

官方 `deployment.multi_instance` 明确支持共享数据库的多个 Gateway 实例，不限于同一进程树的多个 uvicorn worker。它要求 PostgreSQL、数据库 run events、run ownership 心跳、Redis stream bridge，并对浏览器工具、sandbox ownership 和 Scheduler 进行额外约束。

因此可以优先评估“工作机运行原生 Gateway 实例，完整 Agent 在该实例执行”。没有 Fleet 专用 runner，并不等于原生不能把完整 Agent 放在另一台 ECS。

但这只是运行基础。多副本负载均衡不自动提供按任务 profile 选机、持久资源排队、每任务进程隔离、机器预算、物理停止确认，也不能保证 worker 纯出站。上述能力仍需设计和验证，不能用一句“原生支持多实例”全部略过。

### 3.2 原生已有目标续跑，但不是完整依赖编排器

原生 Goal 包含 continuation/no-progress 预算；`external_wait` 会阻止无意义的即时续跑。原生 MCP 通知会幂等发起新的 run，把任务事件交给同一 thread。

这些应作为组合功能的基础。剩余问题是：多个依赖什么时候一起唤醒、目标是否已变更、取消是否阻止旧结果继续执行、通知是否落到正确执行节点，以及等待时资源是否已经真实释放。上一版独立 Agent task 状态机需要据此重新审查，不能默认再造一个目标系统，也不能在没有替代证据时直接删除其保护。

## 4. 三条实现路线与推荐

| 路线 | 好处 | 缺口或成本 | 判断 |
|---|---|---|---|
| 全部只靠原生配置和负载均衡 | 自定义代码最少 | 无法直接满足固定池自动调度、统一资源预算与严格依赖衔接 | 不足以覆盖全部需求 |
| 原生运行时和持久任务 + ECS 执行适配 + 依赖协调 | 保留全部功能，减少平行状态机和核心侵入 | 调度、启动边界、等待/取消衔接仍需少量明确扩展；规模须由验证决定 | 推荐 |
| 延续上一版完整 Fleet 执行协议与独立 runner | 可以定制每个底层语义 | 核心耦合、升级成本和测试面过大 | 不作为默认重做路线 |

推荐的是责任边界，不承诺未验证的代码缩减比例，也不把“薄适配”当作已经证明很简单。

## 5. B：优先接入原生持久 MCP 任务

建议数据流：原生 Agent → MCP submit → ECS 程序执行服务 → 原生 McpTaskService 持久跟踪 → 原生结果通知与文件展示。

普通 MCP driver 已支持配置 submit/status/cancel 工具映射。应先以这个公开接入点验证，避免为接入 B 就扩展 Gateway 的 driver 注册或修改 run 核心。执行服务仍必须保存真正的程序队列、执行尝试与取消状态；MCP 客户端轮询能力不能替代服务端的持久执行。

两个层面的状态各有职责：原生 mcp_tasks 记录用户任务跟踪与通知；执行服务记录容器是否启动、在哪个节点、是否真正退出。两者通过稳定 ID 对应，避免把通知状态、UI 状态和容器状态复制进两套独立业务流程。

程序完成后的产物进入既有授权文件入口。NAS 只是共享存储，不是授权控制，也不是执行完成的证据。

## 6. C：原生运行时远程部署，补执行准入和传输

推荐优先验证常驻原生 Gateway 实例作为工作机的执行端。它继续使用同一 lead Agent、RunManager、checkpoint、用户身份与事件通道。中央新增部分负责等待资源、选择节点和交付执行请求，不编写另一套 graph 驱动循环。

原上下文要求 worker 拉取、纯出站，当前评估继续保留这一约束：

- 若保留纯出站，需要节点侧薄领取组件，将受控执行请求交给本机原生运行时；不能直接用中央 HTTP 调用工作机替代。
- 本机调用也必须携带受限的用户/线程身份与幂等准入信息。管理员令牌不能作为所有用户任务的通用执行身份。
- 中央不能先在本机创建并启动一次 run，再在 worker 创建另一次；真正执行 run 的准入只能发生一次。等待资源的 dispatch 记录与原生 run 记录应有清晰关联。
- 短交互在中央运行、重任务在 worker 运行，两条路径共享线程写入互斥与原生运行归属。
- 原生 checkpoint 能恢复逻辑状态，不承诺迁移仍在运行的 Python 进程、终端会话或浏览器状态。

若本机原生运行时缺少足够窄的可信启动入口，应明确新增该入口，复用完整生命周期。只有验证发现常驻实例无法满足既定隔离或恢复要求，才评估每 run 容器；不能因为旧版已经有该实现就直接延续它。

## 7. B/C 组合与故障语义不能被简化掉

正常链路：C 原生 run 提交 B → 保存原生目标/checkpoint 与依赖引用 → 结束或挂起本轮并释放可释放的执行额度 → B 完成 → 原生任务事件驱动依赖判定 → 同一目标发起新原生 run。

需要保留：

- 等待是有持久记录的状态；不能靠模型在聊天内容中记住 job ID。
- B/C 来自同一资源账；C 等 B 时不能把小机器池占满。
- 常驻 Gateway 的基础内存不会因某个 run 结束而消失，必须作为节点常驻开销扣除；只释放该 run 实际持有的额度。
- 使用原生通知的投递身份与幂等机制，不并行再开第二条重复通知路径；增强“唤醒”的条件不能丢掉正常结果通知。
- 对同一依赖事件只接受一次有效续跑；不宣称外部副作用 exactly-once。
- 用户取消、改目标或插入新消息之后，旧任务结果不能擅自启动旧目标。
- 原生失联协调可能将过期 run 标为 error；这不证明旧机器上的外部命令已停止。执行服务仍须保留停止确认或未知状态，不能立即释放并重复执行。
- 非幂等外部动作在结果不明时必须保留待核对状态；重试策略与 checkpoint 恢复不是同一件事。

这些是全部功能的一部分，不能以减少代码为由删去；但应尽量约束在调度/执行适配层和原生生命周期接点。

## 8. 数据与旧实现怎么处理

继续以原生 users/threads/runs/checkpoints/run events、mcp_tasks、Scheduler、batch 与 goal 状态为权威，不新增平行副本。

只为缺口设计扩展数据：节点与资源准入、程序执行队列和尝试、远程 dispatch 到原生 run 的映射、目标与依赖的关联及幂等唤醒记录。具体合并成多少张表需要在接口验证后确定，本轮不再先冻结大量表结构。

旧实现按责任逐项审计：

| 旧内容 | 重做处理 |
|---|---|
| 容器资源限制、节点健康、停止确认等 | 审查可复用部分，保留必要安全语义 |
| Fleet 专用的任务轮询、通知与页面状态 | 优先由原生 MCP Tasks 机制承担，仅保留执行端需要的映射 |
| 专用 remote runner 与核心运行接口改动 | 先验证原生 Gateway 执行端能否替代，再决定保留哪些窄接点 |
| 独立 agent_tasks/generation/等待组 | 对照原生 goal、通知幂等和线程互斥重新归并，必要的依赖字段仍保留 |
| checkpoint、事件、预算的重复适配 | 以原生实现为主，证明缺口之后才保留扩展 |
| 原有测试与部署代码 | 按最终保留的需求和接口筛选，避免以旧实现细节倒推新设计 |

不直接删除旧分支、表或数据。重做必须区分本分支 Fleet 增量、fork 中其他已有改动、官方后续新增能力；不能通过整仓回退覆盖无关工作。

## 9. 最有效的验证顺序与开机时机

当前阶段保持两台 ECS 停机。本地完成能力证据表、接口选型和最小验证脚本，不进行镜像重建或发布。

方案收敛后再集中开机，按顺序验证：

1. 原生基线：官方能力基线运行真实模型与工具，状态和文件可读取。
2. B 主干：原生 MCP 任务接入程序执行后端，完成提交、跨机执行、结果回流。
3. C 主干：工作机原生运行时实际完成模型与工具循环，中央读取结果并能发起取消。
4. 组合：C 等待 B 后释放执行额度，B 完成后原目标继续；保持纯出站要求。
5. 最小必要故障检查：一次取消、一次进程/服务重启恢复、一次重复事件不重复执行。按实际风险与发现补充，避免先铺完整故障矩阵。
6. 最后统一 Jenkins 发布和重建手册，记录实际运行镜像、配置引用与证据。

前一项不成立时，先定位原生限制或适配缺口，不通过修改验收要求让后续“通过”。每一步以真实用户行为与持久记录证明结果，而不是用模拟测试数量作为进度。
