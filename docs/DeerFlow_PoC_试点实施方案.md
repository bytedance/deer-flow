# DeerFlow PoC 试点实施方案

## 1. 文档目的

本文档用于指导企业或团队基于 DeerFlow 开展第一阶段 PoC 试点，目标不是一次性建设完整平台，而是用最小成本验证：

1. DeerFlow 是否能支撑真实业务场景
2. 当前技术架构是否适合继续投入
3. 企业后续平台化改造应优先补哪些能力

本文面向：

- 技术负责人
- 架构师
- AI 应用研发团队
- 平台 / 运维团队
- PoC 项目经理

## 2. PoC 目标

PoC 阶段的目标要尽量具体，避免“只要能跑就算成功”。

建议把目标控制在以下 4 项：

1. 跑通 1 到 2 个真实业务闭环
2. 让试点用户能稳定完成目标任务
3. 看清 DeerFlow 的可用能力与明显短板
4. 为下一阶段平台化建设提供真实依据

一句话总结：

> PoC 不是证明 DeerFlow “很先进”，  
> 而是证明它“能不能解决我们的真实问题”。

## 3. PoC 范围建议

### 3.1 推荐纳入范围

PoC 建议优先选择下面这类能力：

- 多轮会话
- 流式响应
- 文件上传
- Artifact 输出
- 1 到 2 个 Skills
- 1 到 2 个 MCP / Tool 扩展
- Sandbox 执行

### 3.2 不建议首期纳入范围

为了控制复杂度，PoC 首期不建议一开始就做：

- 全公司统一账号体系
- 完整 RBAC
- 多租户平台后台
- 复杂审批流
- 大规模用户接入
- 公网开放访问

PoC 的正确边界应该是：

- 有真实业务价值
- 有最小共享能力
- 但不过早平台化

## 4. 试点场景选择建议

建议最多选 `2` 个场景，避免试点目标失焦。

### 4.1 推荐场景类型

优先推荐：

1. **研发助手**
   - 代码阅读
   - 文档总结
   - 改造建议
   - 测试建议

2. **文档 / 报告生成助手**
   - 培训教材
   - 方案草稿
   - 技术总结
   - 研究报告

3. **知识与工具编排助手**
   - 查询内部系统
   - 整理输出结果
   - 形成结构化结论

### 4.2 不推荐的试点场景

首期不建议选：

- 极强实时性要求场景
- 强审批、强合规流程场景
- 高度依赖复杂权限体系的场景
- 对数据隔离要求极端严格但又暂时不准备补平台能力的场景

## 5. 推荐试点环境

### 5.1 部署方式

建议：

- `Linux + Docker`
- 内网可信环境
- 小范围共享

不建议：

- 个人电脑临时跑给多人共用
- 没有前置鉴权直接开放
- 首期就面向公网

### 5.2 资源建议

按试点环境建议：

| 环境类型 | 起步配置 | 推荐配置 | 说明 |
| --- | --- | --- | --- |
| 单人验证 | 4 vCPU / 8 GB | 8 vCPU / 16 GB | 更适合研发调试 |
| 小范围共享试点 | 8 vCPU / 16 GB | 16 vCPU / 32 GB | 更适合部门级试点 |

### 5.3 持久化要求

至少要持久化：

- `backend/.deer-flow/memory.json`
- `backend/.deer-flow/agents/*/memory.json`
- `backend/.deer-flow/threads/*`
- 上传目录
- outputs 目录

如果这些目录不持久化，PoC 阶段很容易因为重启丢数据而误判效果。

## 6. PoC 实施工作分解

建议按 5 个工作包推进。

### 工作包 1：环境与基础运行

目标：

- 确保 DeerFlow 可以稳定启动并被试点团队访问

主要任务：

1. 准备试点服务器
2. 部署 DeerFlow 基础服务
3. 配置模型、Sandbox、必要 MCP
4. 配置日志和最小健康检查
5. 配置最小访问控制

阶段产出：

- 可访问的 PoC 环境
- 环境配置说明
- 启动与恢复手册

### 工作包 2：业务场景接入

目标：

- 跑通 1 到 2 个真实业务场景

主要任务：

1. 选择试点场景
2. 拆解场景需要的 Skill / Tool / MCP
3. 接入或配置必要能力
4. 形成最小业务闭环

阶段产出：

- 场景任务清单
- Skill / MCP / Tool 接入清单
- 业务闭环演示路径

### 工作包 3：前端体验最小优化

目标：

- 让试点用户能够“愿意用、会用、知道结果在哪”

主要任务：

1. 明确入口页面与试点导航
2. 优化必要提示文案
3. 明确上传、运行中、报错、Artifact 展示体验
4. 明确试点场景下的推荐操作路径

阶段产出：

- 试点前端入口
- 使用说明
- 常见问题提示

### 工作包 4：试点保障与问题处理

目标：

- 保证试点过程可观测、可定位、可修复

主要任务：

1. 定义问题提交流程
2. 建立最小日志与排障入口
3. 形成试点问题台账
4. 明确升级问题的责任人

阶段产出：

- 试点问题清单
- 排障流程
- 责任分工表

### 工作包 5：效果评估与复盘

目标：

- 判断 DeerFlow 是否值得继续推进到平台化阶段

主要任务：

1. 收集使用反馈
2. 统计成功率、耗时、问题数
3. 分析哪些问题来自业务，哪些问题来自平台能力缺口
4. 输出 PoC 复盘结论

阶段产出：

- PoC 评估报告
- 平台能力缺口清单
- 下一阶段改造建议

## 7. 角色分工建议

### 7.1 技术负责人

负责：

- 确定试点目标与成功标准
- 决定纳入范围与不纳入范围
- 决定是否进入下一阶段平台化投入

### 7.2 架构师 / 后端负责人

负责：

- DeerFlow 架构接入方式
- Skill / MCP / Tool / Sandbox 方案设计
- 风险点识别与技术边界定义

### 7.3 后端工程师

负责：

- Runtime / Gateway / Tool / MCP 改造
- Memory、Sandbox、Artifact 链路调通
- 问题定位与修复

### 7.4 前端工程师

负责：

- 试点入口与页面交互
- 流式体验、上传体验、错误提示
- 场景化前端支撑

### 7.5 平台 / 运维工程师

负责：

- 环境搭建
- 持久化与日志
- 健康检查
- 资源与稳定性保障

### 7.6 测试工程师

负责：

- 冒烟用例
- 场景回归
- 问题复现与归因
- 试点验收支持

### 7.7 业务试点用户

负责：

- 真实使用
- 提交反馈
- 识别业务价值与使用障碍

## 8. 试点成功标准

建议从 4 个维度定义成功标准。

### 8.1 业务成功

至少满足：

- 至少 1 个真实场景可闭环完成
- 用户认为输出结果有实际参考价值

### 8.2 技术成功

至少满足：

- 核心链路稳定可用
- Sandbox、上传、Artifact、Streaming 跑通
- 试点期间没有阻断性系统问题长期未解

### 8.3 使用成功

至少满足：

- 试点用户能独立完成主要操作
- 用户知道如何上传、提问、查看结果、定位问题

### 8.4 推进成功

至少满足：

- 团队能明确下一阶段要补哪些平台能力
- 形成清晰的投入与收益判断

## 9. 推荐验收指标

可选指标如下：

| 指标 | 建议口径 |
| --- | --- |
| 试点用户数 | 5-15 人 |
| 试点场景数 | 1-2 个 |
| 核心任务成功率 | >= 70% |
| 严重阻断问题数 | 越低越好 |
| 用户复用率 | 至少能持续多次使用 |
| 业务认可度 | 用户愿意继续使用或扩展 |

这些指标不一定全部量化到严格考核，但建议至少做趋势记录。

## 10. 试点风险清单

### 10.1 最常见风险

1. 试点范围过大
2. 一开始就想做完整平台能力
3. 场景选择过于理想化
4. 没有明确用户反馈机制
5. 共享环境稳定性不足
6. 把业务问题误判成平台问题，或反过来

### 10.2 风险应对策略

1. 场景控制在 `1-2` 个
2. 用户控制在小范围
3. 平台治理只做最小必要项
4. 问题全部进台账
5. 每周固定复盘

## 11. 推荐实施节奏

### 第 1 周

- 场景确定
- 环境准备
- 角色分工
- 成功标准确认

### 第 2-3 周

- DeerFlow 环境跑通
- Skill / MCP / Tool 接入
- 前端最小试点路径打通

### 第 4-5 周

- 小范围用户试用
- 收集问题
- 修复关键阻断项

### 第 6 周

- 复盘评估
- 形成是否进入下一阶段的结论

## 12. PoC 结束后的决策建议

PoC 完成后，建议只做 3 种决策之一：

### 12.1 继续推进

适用条件：

- 业务价值明确
- 技术链路可控
- 问题主要集中在平台化能力未补齐，而不是 DeerFlow 核心能力失效

### 12.2 缩小范围继续验证

适用条件：

- 有价值，但当前场景太复杂
- 需要重新选择更合适的试点切口

### 12.3 暂停推进

适用条件：

- 试点场景价值不成立
- 团队暂时没有足够平台化投入能力
- 安全、隔离或运维要求超出当前阶段承受范围

## 13. 推荐下一步输出物

PoC 试点实施方案之后，建议继续补 2 份文档：

1. `PoC 试点复盘模板`
2. `平台化能力建设任务拆解`

## 14. 最终建议

如果企业现在刚准备启动 DeerFlow 试点，我的建议是：

1. **从一个真实业务场景开始**
2. **先做部门级内网共享，不直接做全公司平台**
3. **先证明业务价值，再投入平台化能力**
4. **PoC 阶段不追求“全”，而追求“真”**

这会比一开始就做大而全的平台方案更稳，也更容易拿到真正有说服力的结论。
