# 用户可编辑知识库与会话可选引用设计（完善版）

## 1. 背景

当前项目已经具备两套相关能力：

- `memory`：面向用户长期偏好和上下文的结构化记忆，特点是自动提取、自动注入、可人工编辑，但不适合承载大量原始资料。
- `rag`：面向文档检索的向量化知识库能力，当前已具备 `ingest / search / collection` 等基础能力，但仍停留在“按 collection 检索”的底层能力层级，缺少面向用户的“知识库实体”“文档实体”“会话选择实体”。

本设计要实现的能力不是增强 `memory`，而是把当前 RAG 从“底层检索能力”升级为“面向用户的知识库产品能力”。

用户可以在自己的租户范围内创建、编辑、删除多个知识库；每个知识库由若干可编辑文档组成；在会话中，用户可以明确选择是否引用知识库，以及引用哪些知识库；只有被当前会话选中的知识库会参与检索增强。

---

## 2. 为什么不要直接复用 `memory`

`memory` 适合保存：

- 用户偏好
- 长期背景
- 少量高价值事实
- 自动提取出的稳定信息

`memory` 不适合保存：

- 大段原始文档
- 可频繁编辑的资料正文
- 多个独立资料集
- 会话级别的显式选择范围
- 需要检索、删除、重建索引的内容

因此二者职责应保持分离：

- `memory` 继续承担“用户长期画像”
- `knowledge base` 承担“用户显式维护的可检索资料库”

二者都可以注入模型，但来源、生命周期、编辑方式、选择粒度和权限边界都不同。

---

## 3. 目标与非目标

### 3.1 必须满足

1. 每个用户可维护多个私有知识库。
2. 知识库中的文档可创建、编辑、删除。
3. 会话里可以显式选择“不开启知识库 / 开启并选择一个或多个知识库”。
4. 只有当前会话选中的知识库参与检索。
5. 用户只能访问自己的知识库。
6. 尽量复用现有 `rag`、`auth`、`thread metadata`、`thread state` 能力。
7. 文档索引需要具备可重试、可追踪、可避免旧版本覆盖新版本的机制。
8. 会话中的知识库选择必须由服务端校验，不能信任前端传入的 `selected_ids`。
9. 历史消息需要记录当轮知识库选择快照，便于后续回溯和排查。

### 3.2 本期非目标

1. 多用户协作编辑同一知识库。
2. tenant 级共享知识库。
3. 文档细粒度权限。
4. 高级引用渲染系统。
5. 自动从历史对话沉淀知识库。
6. 文件上传导入 PDF / DOCX / Markdown。
7. 跨知识库复杂 rerank 和 citation UI。

## 5. 总体架构设计

推荐拆成四层：

### 5.1 知识库目录层

负责管理业务实体：

- 知识库
- 文档
- 文档版本
- 索引任务
- 用户与租户边界

这一层不直接把 vector store 细节暴露给前端。

### 5.2 向量检索层

继续复用当前 `rag` 管线，负责：

- 文档分块
- embedding
- 写入 vector store
- 删除 chunks
- 检索 chunks
- 多 collection fan-out 查询

### 5.3 会话选择层

负责保存当前 thread 是否启用知识库，以及启用了哪些知识库。

推荐继续复用 thread metadata：

```json
{
  "knowledge_base_selection": {
    "enabled": true,
    "selected_ids": ["kb_1", "kb_2"]
  }
}
```

### 5.4 运行时注入层

负责在模型调用前：

1. 读取 runtime context 或 thread metadata 中的知识库选择。
2. 服务端校验 selected IDs。
3. 解析为当前用户可访问的 active 知识库。
4. 执行多 collection 检索。
5. 合并、去重、截断。
6. 注入 `<knowledge_base>` prompt block。
7. 记录本轮 message 的知识库选择快照和检索 trace。

## 6. 核心建模

## 6.1 知识库实体

建议新增 `knowledge_bases` 表。

字段建议：

```text
id
tenant_id
owner_user_id
name
description
collection_name
visibility
status
document_count
chunk_count
last_indexed_at
last_search_at
created_at
updated_at
deleted_at
```

字段说明：

- `id`：业务侧知识库 ID，前端和 API 都使用它。
- `collection_name`：映射到底层 vector store collection，前端不直接感知。
- `visibility`：建议先固定为 `private`，为后续 `tenant` / `system` 共享知识库预留。
- `status`：建议值为 `active | archived`。
- `deleted_at`：建议使用软删除，降低误删风险，也便于补偿 vector store 删除失败的情况。

建议约束：

```text
unique(tenant_id, owner_user_id, name, deleted_at)
unique(collection_name)
index(tenant_id, owner_user_id, status)
```

---

## 6.2 文档实体

建议新增 `knowledge_base_documents` 表。

字段建议：

```text
id
knowledge_base_id
tenant_id
owner_user_id
title
content
content_format
source_name
content_hash
version
chunk_count
chunk_ids
index_status
index_error
index_job_id
last_indexed_at
content_length
metadata
created_at
updated_at
deleted_at
```

字段说明：

- `content_format`：建议值为 `markdown | text`。
- `content_hash`：用于判断内容是否真的变化，避免重复重建索引。
- `version`：每次正文变化递增，用于防止旧索引任务覆盖新版本。
- `chunk_ids`：Phase 1 可以用 JSON 数组保存，便于删除旧 chunks。
- `index_status`：建议值为 `pending | indexing | ready | failed`。
- `index_job_id`：指向当前最新索引任务。
- `metadata`：预留扩展字段，例如导入来源、标签、外部 URL 等。

建议约束：

```text
index(knowledge_base_id, deleted_at)
index(tenant_id, owner_user_id)
index(index_status)
```

---

## 6.3 索引任务实体

这是完善版中建议新增的关键模型，用于解决索引一致性和失败重试问题。

建议新增 `knowledge_base_document_index_jobs` 表。

字段建议：

```text
id
document_id
knowledge_base_id
tenant_id
owner_user_id
version
status
old_chunk_ids
new_chunk_ids
error
started_at
finished_at
created_at
updated_at
```

`status` 建议值：

```text
pending | running | ready | failed | canceled
```

设计原则：

1. 每次文档创建或正文编辑，都生成一个新的 index job。
2. index job 必须绑定文档当时的 `version`。
3. 只有当 job.version 等于 document.version 时，才允许回写文档的 `chunk_ids` 和 `index_status=ready`。
4. 如果用户快速连续编辑，旧 job 即使后完成，也不能覆盖新版本。
5. ingest 成功但 DB 回写失败时，可以通过 job 表排查和补偿。
6. 删除旧 chunks 建议在新版本 ready 后执行，避免编辑失败导致文档暂时不可检索。

---

## 6.4 可选：chunk 明细表

Phase 1 可以暂时只用文档表里的 `chunk_ids` JSON 数组。

但中长期建议新增：

```text
knowledge_base_document_chunks
- id
- document_id
- knowledge_base_id
- tenant_id
- owner_user_id
- version
- chunk_id
- collection_name
- chunk_index
- token_count
- created_at
- deleted_at
```

好处：

- 排查索引问题更容易。
- 删除和补偿更可靠。
- 统计 chunk 数更准确。
- 后续 citation 和检索 trace 更容易落地。

## 6.5 会话知识库选择

thread metadata 中保存线程级默认选择：

```json
{
  "knowledge_base_selection": {
    "enabled": true,
    "selected_ids": ["kb_1", "kb_2"]
  }
}
```

语义约定：

- `enabled=false`：当前会话完全不引用知识库。
- `enabled=true` 且 `selected_ids=[]`：视为不引用。
- `selected_ids` 只表示前端用户选择，不等价于最终可检索集合。
- 服务端必须重新按 `tenant_id + owner_user_id + selected_ids + status=active + deleted_at is null` 解析。

---

## 6.6 消息级选择快照

为了让历史对话可回溯，建议每次发送用户消息时，在 message metadata 中保存当轮选择快照。

示例：

```json
{
  "knowledge_base_selection_snapshot": {
    "enabled": true,
    "selected_ids": ["kb_1"],
    "resolved_kbs": [
      {
        "id": "kb_1",
        "name": "产品资料",
        "collection_name": "kb_user_xxx_001"
      }
    ]
  },
  "knowledge_base_retrieval_trace": {
    "query": "用户本轮问题",
    "per_kb_hits": [
      {
        "kb_id": "kb_1",
        "hit_count": 4,
        "latency_ms": 120
      }
    ],
    "final_chunk_count": 4
  }
}
```

说明：

- thread metadata 表示“当前默认选择”。
- message metadata 表示“当轮实际选择快照”。
- 历史消息回放、问题排查、用户追问都应优先参考 message snapshot。

## 7. 为什么推荐“一个知识库对应一个 collection”

当前 RAG 基础设施是按 collection 检索：

```text
search(query, collection)
ingest(text, collection)
delete(collection, chunk_ids)
```

因此 Phase 1 最小改造路径是：

- 每个知识库对应一个独立 collection。
- 会话里若选择多个知识库，则后端对多个 collection 并行检索，再合并结果。

优点：

1. 与现有 `rag.py / retrieval.py / vector_store.py` 更兼容。
2. 删除整个知识库时可以直接删除 collection。
3. 文档更新时只需按 `chunk_ids` 清理旧数据。
4. Phase 1 不必重写 vector store 抽象。
5. 知识库之间天然隔离，降低误检索风险。

代价：

- 多知识库选择时需要 fan-out 查询。
- 不同 collection 的 score 可能不完全可比。
- 知识库数量多时会增加延迟。

结论：

Phase 1 继续采用“一个知识库一个 collection”是合理的，但必须补充 fan-out 合并、timeout、去重和 trace 机制。

## 8. 文档写入、编辑与删除流程

## 8.1 创建知识库

流程：

1. 服务端读取当前用户上下文，得到 `tenant_id` 和 `owner_user_id`。
2. 生成业务 `kb_id`。
3. 生成底层 `collection_name`。
4. 写入 `knowledge_bases`。
5. 返回知识库详情。

注意：

- 前端不能提交 `tenant_id`、`owner_user_id`、`collection_name`。
- `collection_name` 不应暴露为用户可编辑字段。

---

## 8.2 创建文档

流程：

1. 校验用户是否拥有该知识库。
2. 保存文档正文到 `knowledge_base_documents`。
3. 设置：
   - `version=1`
   - `index_status=pending`
   - `content_hash=hash(content)`
4. 创建 `knowledge_base_document_index_jobs`。
5. 执行索引任务。
6. ingest 成功后回写：
   - `chunk_ids`
   - `chunk_count`
   - `index_status=ready`
   - `last_indexed_at`
7. 更新知识库：
   - `document_count`
   - `chunk_count`
   - `last_indexed_at`

---

## 8.3 编辑文档

推荐采用版本化重建流程。

流程：

1. 读取当前文档记录。
2. 校验用户是否拥有该文档所属知识库。
3. 比较 `content_hash`。
4. 如果正文没有变化，只更新 title / metadata，不重建索引。
5. 如果正文变化：
   - `version += 1`
   - 保存新正文
   - `index_status=pending`
   - 创建 index job，记录 `old_chunk_ids`
6. 执行新版本 ingest。
7. ingest 成功后检查：
   - `job.version == document.version`
   - `job.status` 仍有效
8. 校验通过后回写新 `chunk_ids`。
9. 将文档标记为 `ready`。
10. 异步或补偿式删除旧 `chunk_ids`。

关键规则：

- 旧 job 不得覆盖新 version。
- 新索引未 ready 前，可以继续保留旧 chunks，以保证文档仍可检索。
- 若新索引失败，文档显示 `failed`，但旧 chunks 可继续保留，避免知识库完全失效。

---

## 8.4 删除文档

流程：

1. 校验用户是否拥有该文档所属知识库。
2. 软删除文档：设置 `deleted_at`。
3. 将文档标记为不可检索。
4. 删除 vector store 中对应 `chunk_ids`。
5. 更新知识库的 `document_count` 和 `chunk_count`。
6. 若删除 vector chunks 失败，记录补偿任务或保留错误状态。

注意：

- 查询文档列表时默认过滤 `deleted_at is null`。
- 检索时 chunk metadata 里如果能带 `document_id/version`，可额外防御已删除文档误召回。

---

## 8.5 删除知识库

流程：

1. 校验用户是否拥有该知识库。
2. 将知识库软删除：设置 `deleted_at` 或 `status=archived/deleted`。
3. 将该知识库下文档软删除。
4. 删除底层 vector collection。
5. 清理 thread metadata 中已经选择的该知识库，或在读取时自动过滤。
6. 若 vector collection 删除失败，记录补偿任务。

建议策略：

- API 层对用户表现为“已删除”。
- 底层 collection 删除失败不阻塞用户视角的删除成功，但必须记录错误并可重试。

---

## 9. 检索流程设计

## 9.1 会话检索主流程

1. 前端发送消息时，把当前 `knowledge_base_selection` 放进 runtime context。
2. 后端读取 runtime context。
3. 如果 context 中没有选择，则 fallback 到 thread metadata。
4. 服务端 normalize 选择：
   - `enabled=false`：跳过知识库检索。
   - `enabled=true` 但 `selected_ids=[]`：跳过知识库检索。
5. 服务端按当前用户过滤并解析知识库：
   - `tenant_id == current tenant`
   - `owner_user_id == current user`
   - `id in selected_ids`
   - `status == active`
   - `deleted_at is null`
6. 对 resolved KBs 执行多 collection fan-out 检索。
7. 合并、去重、截断。
8. 注入 `<knowledge_base>` prompt block。
9. 保存 message metadata：
   - selection snapshot
   - retrieval trace

---

## 9.2 服务端选择解析逻辑

伪代码：

```python
def resolve_knowledge_base_selection(selection, current_user):
    if not selection or not selection.enabled:
        return []

    selected_ids = selection.selected_ids or []
    if not selected_ids:
        return []

    kbs = knowledge_base_repo.list_by_ids(
        tenant_id=current_user.tenant_id,
        owner_user_id=current_user.id,
        ids=selected_ids,
        status="active",
        deleted_at=None,
    )

    return kbs
```

规则：

- 前端传入的 `selected_ids` 只能作为候选。
- 最终可检索知识库必须由服务端查询得到。
- 不存在、已归档、已删除、非 owner 的知识库不得参与检索。

---

## 9.3 多知识库 fan-out 合并策略

建议 Phase 1 采用简单、可控、可观测的合并策略。

参数建议：

```text
top_k_per_kb = 5
max_injection_chunks = 8
per_kb_timeout_ms = 1500
max_selected_kbs = 5
max_total_retrieval_timeout_ms = 3000
max_chunks_per_document = 3
```

流程：

1. 对每个 selected KB 并行发起检索。
2. 每个 KB 最多返回 `top_k_per_kb` 个 chunk。
3. 单个 KB 超时不影响其他 KB 返回。
4. 合并所有 hits。
5. 按以下规则去重：
   - 相同 `chunk_id` 去重。
   - 相同 `document_id + version + chunk_index` 去重。
   - 可选：相似文本 hash 去重。
6. 限制同一 document 最多注入 `max_chunks_per_document` 个 chunk。
7. 按 score 排序。
8. 截断到 `max_injection_chunks`。
9. 记录 retrieval trace。

注意：

- 不同 collection 的 score 可能不完全可比，Phase 1 可以先直接排序。
- 如果效果不稳定，Phase 2 再增加 reranker 或 score normalization。

---

## 9.4 Prompt 注入格式

建议注入结构化 block：

```xml
<knowledge_base>
  <source kb_id="kb_1" kb_name="产品资料" document_id="doc_1" document_title="价格规则" version="3">
    <![CDATA[
    chunk content...
    ]]>
  </source>
  <source kb_id="kb_2" kb_name="客户问答" document_id="doc_9" document_title="售后政策" version="1">
    <![CDATA[
    chunk content...
    ]]>
  </source>
</knowledge_base>
```

chunk metadata 至少包含：

```text
kb_id
kb_name
document_id
document_title
source
version
chunk_id
chunk_index
```

好处：

- 模型更容易说明来源。
- 后续做 citation UI 时不需要重建底层数据。
- 排查错误召回更容易。

---

## 9.5 runtime context 与 thread metadata 的优先级

建议约定：

1. 本轮消息明确携带 runtime context 时，以 runtime context 为准。
2. runtime context 缺失时，读取 thread metadata。
3. 发送消息成功后，如果前端已经持久化 thread metadata，则不额外修改。
4. 如果是新线程首轮消息，可在创建 thread 时一并写入 metadata。

关键点：

- runtime context 是“本轮请求携带的选择”。
- thread metadata 是“线程默认选择”。
- message metadata 是“当轮实际使用快照”。

## 10. 后端接口设计

建议新增业务接口，不继续把面向用户的知识库产品能力挂在 `/api/rag` 下。

---

## 10.1 知识库接口

```text
GET    /api/knowledge-bases
POST   /api/knowledge-bases
GET    /api/knowledge-bases/{kb_id}
PATCH  /api/knowledge-bases/{kb_id}
DELETE /api/knowledge-bases/{kb_id}

## 13. 运行时注入设计

当前 `RagMiddleware` 是“拿最后一条用户消息，去默认 collection 检索”。

建议改成：

1. 从 `runtime.context` 或 thread metadata 读取 `knowledge_base_selection`。
2. 如果未启用或未选择，直接跳过。
3. 服务端校验 `selected_ids`。
4. 解析为对应 `collection_name`。
5. 执行多 collection fan-out 检索。
6. 合并、去重、截断。
7. 格式化为 `<knowledge_base>` block。
8. 注入 prompt。
9. 保存本轮 message metadata。

伪代码：

```python
async def maybe_inject_knowledge_base(context, thread, user, last_user_message):
    selection = context.get("knowledge_base_selection") \
        or thread.metadata.get("knowledge_base_selection")

    resolved_kbs = resolve_knowledge_base_selection(selection, user)
    if not resolved_kbs:
        return None

    results, trace = await kb_retriever.search_many(
        query=last_user_message.content,
        knowledge_bases=resolved_kbs,
        top_k_per_kb=5,
        max_chunks=8,
        timeout_ms=3000,
    )

    if not results:
        return None

    prompt_block = format_knowledge_base_block(results)

    save_message_metadata(
        selection_snapshot=build_selection_snapshot(selection, resolved_kbs),
        retrieval_trace=trace,
    )

    return prompt_block
```

## 14. 权限与隔离

### 14.1 所有权

知识库所有权必须完全由服务端决定：

```text
owner_user_id = current_user.id
tenant_id = current_user.tenant_id
```

前端不允许提交：

- `owner_user_id`
- `tenant_id`
- `collection_name`

---

### 14.2 查询边界

所有知识库相关路由都必须自动带上：

```text
tenant_id == current tenant
owner_user_id == current user
deleted_at is null
```

这个约束建议下沉到 repository/service 层，而不是只放在 router 层。

---

### 14.3 会话选择安全

以下情况不得参与检索：

- `selected_ids` 中包含他人知识库。
- `selected_ids` 中包含不存在的知识库。
- `selected_ids` 中包含已删除知识库。
- `selected_ids` 中包含 archived 知识库。
- `selected_ids` 超过系统限制。

推荐处理策略：

- 对普通失效 ID：静默过滤并记录 trace。
- 对明显越权 ID：返回 403 或记录安全日志，取决于现有安全策略。

---

### 14.4 no-auth 模式

如果系统处于 no-auth 模式，则退化为：

```text
user_id = "default"
tenant_id = "default"
```

建议增加显式配置：

```text
ALLOW_NO_AUTH_KB=true/false
```

避免生产环境误启 no-auth 后所有知识库都落到默认用户。

## 17. 测试建议

## 17.1 后端测试

### CRUD 与权限

- 当前用户可以创建、读取、编辑、删除自己的知识库。
- 当前用户无法读取他人的知识库。
- 当前用户无法把文档写入他人的知识库。
- `tenant_id` 和 `owner_user_id` 由服务端生成，前端传入无效。
- archived / deleted 知识库不可参与检索。

### 文档索引

- 创建文档后生成 index job。
- ingest 成功后文档变为 `ready`。
- ingest 失败后文档变为 `failed`，错误信息可见。
- 手动 reindex 可以恢复 failed 文档。
- 文档正文未变化时不重复重建索引。
- 文档更新时旧 `chunk_ids` 被正确清理。

### 版本一致性

- 文档连续快速编辑，旧 index job 不得覆盖新版本。
- 旧 job 完成时如果 version 不匹配，应标记为 canceled 或 ignored。
- 新索引失败时旧 chunks 可以继续保留。

### 删除与补偿

- 删除文档后对应 chunks 被删除。
- 删除知识库后底层 collection 被删除。
- vector store 删除失败时记录补偿信息。
- 已删除知识库仍出现在 thread metadata 时不会参与检索。

### 会话选择

- `enabled=false` 时不检索。
- `enabled=true` 但 `selected_ids=[]` 时不检索。
- runtime context 与 thread metadata 不一致时，以 runtime context 为准。
- selected_ids 中混入他人 KB 时不得参与检索。
- selected_ids 中混入 archived/deleted KB 时不得参与检索。

### 多知识库检索

- 多知识库 fan-out 检索结果能正确合并排序。
- 单个 KB 检索超时不影响其他 KB。
- 同一 chunk 不重复注入。
- 同一 document 不超过 `max_chunks_per_document`。
- 最终注入数量不超过 `max_injection_chunks`。
- retrieval trace 正确记录。

- 知识库列表展示正常。
- 创建、重命名、删除知识库交互正常。
- 文档创建、编辑、删除正常。

## 19. 关键风险与应对

### 风险 1：索引状态不一致

表现：

- DB 显示 ready，但 vector store 没有 chunks。
- vector store 有旧 chunks，但文档已经更新。
- 快速连续编辑后旧版本覆盖新版本。

应对：

- 引入 index job。
- 所有索引任务绑定 document version。
- 回写前做 version guard。
- 保留 retrieval trace 和 index job 日志。

---

### 风险 2：越权检索

表现：

- 前端传入他人的 `kb_id`。
- thread metadata 中残留已删除或不可访问 KB。

应对：

- 所有 selected IDs 服务端重新解析。
- repository 层统一加 `tenant_id + owner_user_id` 过滤。
- archived/deleted KB 不参与检索。

---

### 风险 3：多知识库检索质量不稳定

表现：

- 某个知识库结果过多，挤掉其他知识库。
- 不同 collection 的 score 不可比。
- 重复 chunk 被注入。

应对：

- per-KB top_k。
- max chunks per document。
- 去重。
- trace。
- Phase 2 增加 reranker 或 score normalization。

---

### 风险 4：延迟变高

表现：

- 选择多个知识库后响应变慢。

应对：

- 限制 `max_selected_kbs`。
- 并行检索。
- per-KB timeout。
- overall timeout。
- 超时降级，不阻塞整轮回答。

---

### 风险 5：历史回答不可解释

表现：

- 用户回看历史回答时，不知道当时引用了哪些知识库。

应对：

- thread metadata 保存当前默认选择。
- message metadata 保存当轮选择快照。
- retrieval trace 保存最终召回 chunks 摘要。

---

## 20. 最终建议

这项功能最合理的实现方式是：

- 用新的 `knowledge base catalog` 承接“知识库 / 文档 / 权限 / 索引任务”。
- 用现有 `rag` 承接“分块 / 嵌入 / 检索 / 删除”。
- 用 `thread metadata` 承接“当前会话默认引用哪些知识库”。
- 用 `message metadata` 承接“本轮实际引用哪些知识库”。
- 用 `RagMiddleware` 完成服务端解析、鉴权、fan-out 检索和 prompt 注入。

首期应优先保证：

```text
P0：用户私有知识库 CRUD
P0：文档 CRUD + 索引任务 + version guard
P0：服务端校验 selected_ids
P0：RagMiddleware 只检索当前会话选中的知识库
P0：message metadata 保存当轮选择快照
P1：fan-out 检索 timeout、去重、trace
P1：文档 reindex 接口
P1：前端展
