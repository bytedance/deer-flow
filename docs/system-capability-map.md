# DeerFlow 系统能力地图

最后更新：2026-05-21

## 1. 目的

本文档从系统能力、产品边界、交付分层三个维度，对 DeerFlow 当前已实现的功能进行归类和审视。

它不是接口清单，也不是代码架构细节说明。它面向以下场景：

- 架构评审：回答“系统到底由哪些能力域组成”
- 路线图讨论：回答“下一阶段应该强化哪条主线”
- 项目管理：回答“哪些模块已经形成闭环，哪些仍处于建设期”
- 产品沟通：回答“DeerFlow 是通用 Agent 平台，还是行业化解决方案”

## 2. 系统定义

当前 DeerFlow 不应再被简单定义为“一个 AI 对话应用”。从实现和功能面看，它已经是一个复合型平台，由以下几层组成：

- 前端工作台：承载聊天、知识库、报告、闭环、管理后台等主要用户入口
- Agent 运行时：基于 LangGraph 的线程、运行、流式事件、工具编排与中间件体系
- 平台网关：提供模型、技能、MCP、连接器、租户、认证、治理等非运行时能力
- 可扩展能力层：模型、技能、MCP Server、HTTP Connector、自定义 Agent
- 业务结果层：知识库、报告模板、报告运行、闭环工单
- 企业与行业集成层：认证、组织、设备、渠道与 InS 相关能力

从产品角度看，聊天只是入口，不是系统的完整定义。系统的真正价值在于把“执行能力、知识能力、产出能力、治理能力”组合成一个可运营的平台。

## 3. 能力域划分

### 3.1 Agent Workspace

这是当前系统最成熟的主能力域，负责承载用户与 Agent 的直接交互。

包含能力：

- 对话线程与运行管理
- 流式响应与事件回放
- 文件上传与产物管理
- 反馈与建议
- 动态 UI 交互

典型用户：

- 普通业务用户
- 高阶分析用户

主要价值：

- 提供统一工作入口
- 将“提问、执行、查看结果、继续追问”串成单一体验

关键依赖：

- LangGraph 运行时
- Sandbox
- 工具层
- 模型层

成熟度：`L4`

判断依据：

- 前后端入口完整
- 生命周期清晰
- 能力之间已形成强关联

### 3.2 Agent Capability Platform

该能力域决定 Agent “能做什么”和“怎么被扩展”。

包含能力：

- 模型管理
- Skills 管理
- MCP Server 配置
- HTTP Connector 配置
- 自定义 Agent
- 租户级 Agent / MCP / Connector

典型用户：

- 平台配置者
- AI 应用构建者
- 租户管理员

主要价值：

- 把 Agent 的可用能力从代码中抽离出来
- 让系统具备平台化扩展性

关键依赖：

- Gateway 配置与持久化
- 租户模型
- 权限与治理模型

成熟度：`L3.5`

判断依据：

- 技术扩展点已较丰富
- 但普通用户视角下的“产品化配置体验”仍不完全统一

### 3.3 Knowledge & Retrieval

该能力域负责把“文档”变成“可被 Agent 消费的知识”。

包含能力：

- 知识库创建与权限
- 文档上传与索引
- 重建索引与恢复
- 检索与跨知识库检索
- RAG 管理接口

典型用户：

- 知识管理员
- 高阶业务用户
- 报告使用者

主要价值：

- 让系统从会话式问答走向组织知识复用
- 为报告、分析和长期任务提供稳定上下文

关键依赖：

- 上传能力
- Embedding / Vector Store
- 权限模型
- 后台索引调度

成熟度：`L3.5`

判断依据：

- 能力完整度较高
- 后台机制成熟
- 但产品主线仍需与聊天、报告进一步收敛

### 3.4 Report & Outcome

该能力域负责把 Agent 的过程性输出沉淀为结构化结果。

包含能力：

- 报告模板
- 模板版本化
- 模板校验与发布
- 报告运行记录
- 报告产物读取

典型用户：

- 分析用户
- 运营人员
- 管理层接收者

主要价值：

- 把一次性回答转成可复用、可回溯、可审查的业务产物

关键依赖：

- Agent Workspace
- 知识库与工具
- 模板 DSL
- 权限模型

成熟度：`L3`

判断依据：

- 已具备单独产品域雏形
- 但当前仍更像强功能模块，而不是系统第一主入口

### 3.5 Closed Loop & Governance

该能力域负责把“发现问题”转成“可追踪的组织动作”。

包含能力：

- 闭环工单
- 状态流转
- 成本/预算
- 管理后台
- 审计与日志
- 租户治理

典型用户：

- 租户管理员
- 平台管理员
- 运维与管理角色

主要价值：

- 让系统具备企业级控制面
- 把 Agent 输出延伸到组织执行

关键依赖：

- 认证与租户
- 权限模型
- 报告与诊断结果

成熟度：`L2.5-L3`

判断依据：

- 方向正确
- 已形成基础闭环
- 但整体更偏控制面，业务一线使用深度仍需加强

### 3.6 Enterprise / Industry Integration

该能力域负责接入企业现有身份、组织、设备与外部系统。

包含能力：

- 本地认证与 ins-base 认证
- 组织树 / 设备 / 测点相关接口
- IM 渠道能力
- InS 相关数据接入

典型用户：

- 企业客户
- 行业方案实施方
- 内部解决方案团队

主要价值：

- 将 DeerFlow 从通用平台推向行业解决方案

关键依赖：

- 外部系统稳定性
- 网关认证
- 数据映射与组织模型

成熟度：`L2.5`

判断依据：

- 集成点较多
- 但产品边界尚不清晰，通用能力与行业能力仍存在耦合

## 4. 能力域关系图

建议将当前系统理解为一条主业务链和两条支撑链。

主业务链：

`用户/任务 -> Agent Workspace -> 能力调用 -> 知识/数据 -> 结果产出 -> 闭环执行 -> 组织沉淀`

支撑链一：

`模型/技能/MCP/Connector/Agent 配置 -> 决定 Agent 能力边界`

支撑链二：

`认证/租户/预算/审计/管理后台 -> 决定系统治理边界`

这意味着：

- `Workspace` 是统一入口
- `Capability Platform` 是能力供给层
- `Knowledge & Report` 是价值放大层
- `Governance` 是企业化控制层
- `Industry Integration` 是面向垂直场景的增强层

## 5. 成熟度矩阵

| 能力域 | 当前成熟度 | 当前状态 | 主要风险 | 战略角色 |
| --- | --- | --- | --- | --- |
| Agent Workspace | L4 | 核心主线，已形成闭环 | 后续需求过多导致主链复杂化 | 平台入口 |
| Agent Capability Platform | L3.5 | 技术扩展能力强 | 平台化治理和产品化配置体验不足 | 平台底座 |
| Knowledge & Retrieval | L3.5 | 后台机制较成熟 | 与主工作台、报告链路耦合仍可加强 | 知识中台 |
| Report & Outcome | L3 | 已具备独立产品域雏形 | 入口权重不足，价值感知分散 | 结果沉淀层 |
| Closed Loop & Governance | L2.5-L3 | 具备控制面基础 | 使用链条尚未完全高频化 | 企业控制面 |
| Enterprise / Industry Integration | L2.5 | 集成面广 | 通用与行业边界不清 | 行业方案层 |

成熟度定义：

- `L4`：主要用户链路已闭环，前后端和数据生命周期清晰
- `L3`：能力完整可用，但仍需边界整合或体验增强
- `L2`：方向明确，已有实现，但产品和治理模型未稳定

## 6. 产品边界建议

当前系统最大的战略问题不是“功能不够”，而是“功能边界表达不够清楚”。

建议将对外叙事拆成三层：

### 6.1 Core Platform

建议包含：

- Agent Workspace
- Agent Capability Platform
- 基础 Knowledge 能力

定位：

- 通用 Agent 工作台与运行平台

### 6.2 Enterprise Control Plane

建议包含：

- 认证
- 租户
- 成本与预算
- 审计
- 闭环治理

定位：

- 企业部署和运营控制面

### 6.3 Industry Solution Layer

建议包含：

- InS 认证与组织
- 设备与测点
- 行业化报告与诊断链路

定位：

- 面向特定行业的解决方案增强层

如果不做这层切分，系统会长期处于“既像平台、又像垂直 SaaS、还像内部解决方案”的混合状态，给研发、销售、产品定义和交付带来持续摩擦。

## 7. 项目管理视角的关键结论

### 7.1 当前不是继续平铺功能的阶段

继续添加零散模块会让系统复杂度超过协作收益。后续更需要按能力域推进，而不是按单个页面或单个接口推进。

### 7.2 应按能力线组织迭代

建议至少拆成四条交付线：

- 核心工作台线：线程、运行、上传、产物、消息交互
- 知识与报告线：知识库、检索、模板、报告运行
- 平台治理线：认证、租户、预算、审计、权限
- 行业解决方案线：InS、设备、组织、行业化模板

### 7.3 最需要补的是“成熟度管理”而不是“功能扩容”

每个能力域都应明确：

- 谁是目标用户
- 谁是维护责任方
- 是否有前端主入口
- 是否有运营流程
- 是否处于实验、可用、核心三种状态之一

目前最缺的是这一层，而不是接口数量。

## 8. 路线图建议

### 阶段一：收敛主产品主线

目标：

- 明确 DeerFlow 的第一主线是 `任务/对话 -> 知识/工具 -> 报告/产物 -> 闭环`
- 统一主工作台入口、术语和生命周期

优先事项：

- 统一工作台内的导航和域模型
- 收敛线程、运行、报告、闭环之间的跳转逻辑
- 减少用户对“系统里到底有几套对象模型”的感知成本

### 阶段二：平台化治理

目标：

- 把可扩展能力真正抽象成平台配置层

优先事项：

- 模型、技能、MCP、Connector、Agent 的统一治理视图
- 发布、启停、权限、审计和依赖关系管理
- 租户级配置与全局配置的边界明确化

### 阶段三：行业方案分层

目标：

- 把行业相关能力从通用平台中显式分层

优先事项：

- InS 认证与组织模型边界清晰化
- 行业模板、行业报告、行业诊断能力打包
- 通用能力与行业能力的发布面分离

## 9. 组织与协作建议

如果系统继续扩展，建议至少在协作上遵守以下原则：

- 平台底座能力和行业能力避免在同一需求中混改
- 认证、租户、权限变更必须视为跨域变更
- 报告、知识库、闭环不应分别孤立演进，应按结果闭环联动设计
- 面向用户的能力必须优先确认前端入口和操作链，而不是先有后端接口

## 10. 当前未决问题

以下问题在现阶段无法从代码和已有文档中直接得出确定答案，需要产品或管理层明确：

- DeerFlow 对外的一号产品定义是什么：通用平台、企业工作台，还是行业解决方案底座
- 行业化能力是否会长期与 Core Platform 同仓同发版
- 租户级能力是否允许真正的独立发布与独立配置策略
- 报告与闭环是否会成为核心主流程，而不是附属模块
- 各能力域的实际业务 owner 和技术 owner 如何划分

## 11. 建议的后续动作

建议基于本文档，继续维护三份配套材料：

- [能力矩阵](./system-capability-matrix.md)：能力域、目标用户、入口、依赖、成熟度、owner、状态
- 边界图：Core Platform / Enterprise Control Plane / Industry Solution Layer
- [路线图草案](./roadmap-2026-06-to-2026-08.md)：按能力域排期，而不是按模块罗列需求

在没有这三份材料之前，继续扩展功能会越来越依赖“人脑中的隐含共识”，而不是清晰的系统边界。
