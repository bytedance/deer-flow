## 1. 使用说明

本文档把现有能力地图和三个月路线图继续下钻成可执行 issue 列表。

拆解原则：

- 每个 issue 都是可单独验收的纵切片，不按前端、后端、网关、文档做横向拆分
- 每个 issue 完成后，都应该能独立演示、验证或进入稳定管理
- `HITL` 表示需要人参与评审或拍板
- `AFK` 表示可以直接进入实现、联调和回归

优先级口径：

- `P0`：不完成会阻塞本周期主线
- `P1`：重要但可排在主阻塞项之后
- `P2`：建议纳入本周期，但不应挤占主链资源

建议建单顺序：

1. 先建所有 `HITL` 决策单
2. 再建被 `P0` 主链依赖的 `AFK` 交付单
3. 最后建治理补强和分层收口单

## 3. 详细 Issue

### ISSUE-01 建立 DeerFlow 第一主流程与对象模型基线

- 类型：`HITL`
- 优先级：`P0`
- 目标月份：`2026-06`
- 建议 Owner：工作台产品负责人 + Agent Runtime 负责人
- Blocked by：None - can start immediately

#### Parent

- 路线图目标 A：收敛主产品主线
- 工作流 1：核心工作台

#### What to build

明确 DeerFlow 当前周期的第一主流程，固定“任务/对话 -> 工具/知识 -> 报告/产物 -> 闭环/治理”的主链定义，并同步定版主对象模型，包括 thread、run、upload、artifact、knowledge base、report run、closure ticket 的业务含义、生命周期边界和主要跳转关系。

这不是纯文档整理，而是一个跨产品、前端、网关、运行时的统一基线。如果这一步不先收敛，后续实现会继续沿着不同对象模型分叉。

#### Acceptance criteria

- [ ] 有一版被产品、架构、前后端共同认可的第一主流程图
- [ ] 有一版主对象模型清单，明确每个对象的职责、状态和关系
- [ ] 明确工作台一级导航中哪些页面属于主入口，哪些属于扩展域
- [ ] 所有仍未拍板的问题被单独列出，不混在主流程定义里

### ISSUE-02 统一工作台执行生命周期与状态语义

- 类型：`AFK`
- 优先级：`P0`
- 目标月份：`2026-06`
- 建议 Owner：Agent Runtime 负责人 + Gateway 文件链路负责人
- Blocked by：`ISSUE-01`

#### Parent

- 路线图目标 A：收敛主产品主线
- 工作流 1：核心工作台

#### What to build

把 thread、run、upload、artifact 在前端和后端的生命周期、状态名称、失败语义和可恢复动作统一起来。用户需要能分清“执行中、已完成、失败、外部依赖不可用、等待索引、等待人工处理”等状态，运维也要能从日志和事件中定位同一条主链上的失败位置。

该 issue 完成后，工作台主链不再依赖零散状态拼装，而是有统一状态口径和回归测试覆盖。

#### Acceptance criteria

- [ ] thread、run、upload、artifact 的状态名称和含义在前后端一致
- [ ] 用户可以在主链中看到失败发生在哪一层，以及下一步动作
- [ ] 常见失败场景至少覆盖执行失败、上传失败、外部依赖不可用三类
- [ ] 关键状态映射和错误语义有回归测试

### ISSUE-03 打通聊天结果、报告结果与产物跳转链路

- 类型：`AFK`
- 优先级：`P0`
- 目标月份：`2026-06`
- 建议 Owner：工作台产品负责人 + 前端交互框架负责人
- Blocked by：`ISSUE-01`, `ISSUE-02`

#### Parent

- 路线图目标 A：收敛主产品主线
- 工作流 1：核心工作台

#### What to build

让用户可以从聊天结果跳到报告结果和产物，也可以从报告和产物反向回到源 thread/run。目标是消除“页面能访问，但链路无法追踪”的断点，让结果消费与生成上下文形成闭环。

该 issue 是主流程的体验收敛单，应该覆盖入口、详情、回跳、上下文标识和最小可追踪信息。

#### Acceptance criteria

- [ ] 从聊天结果能直达相关报告结果或产物
- [ ] 从报告结果或产物能回到对应的 thread/run 上下文
- [ ] 主链页面之间不存在无法回溯来源的死角页面
- [ ] 关键跳转链路具备最小可观测标识，便于排查断链问题

### ISSUE-04 打通上传到报告的知识主链

- 类型：`AFK`
- 优先级：`P0`
- 目标月份：`2026-06`
- 建议 Owner：知识产品负责人 + RAG / Indexing 负责人
- Blocked by：`ISSUE-01`

#### Parent

- 路线图目标 A：收敛主产品主线
- 工作流 2：知识与报告

#### What to build

建立一条可稳定演示的主链：用户上传文档，系统建立或更新索引，运行过程能够检索到该知识，并在报告或结果产物中可见其被消费。重点不是多高级算法，而是让“上传 -> 索引 -> 检索 -> 报告使用”从产品和工程两个视角都成为清晰主流程。

#### Acceptance criteria

- [ ] 用户可以沿单一路径完成上传、等待索引、检索使用和报告消费
- [ ] 索引未完成、索引失败、权限不满足时有明确用户提示
- [ ] 知识库权限在工作台、报告和检索链路中保持一致
- [ ] 主链至少有一条端到端验证路径或集成测试

### ISSUE-05 固化真实 owner、模块状态与投资结论

- 类型：`HITL`
- 优先级：`P0`
- 目标月份：`2026-06`
- 建议 Owner：项目经理 + 产品负责人 + 技术负责人
- Blocked by：`ISSUE-01`

#### Parent

- 路线图目标 A：收敛主产品主线
- 跨工作流治理基础

#### What to build

把当前“建议 owner”升级成真实 owner 台账，并对每个模块给出 Core、Scale-Up、Stabilize、Incubate 的状态结论，以及 Q3 是否继续投资的明确判断。没有 owner 的模块需要显式标记，不允许继续隐性漂浮。

#### Acceptance criteria

- [ ] 能力矩阵中的每个模块都有真实业务 owner 和技术 owner
- [ ] 每个模块都标注当前状态和本周期投资结论
- [ ] 仍未定责的模块被显式列为管理风险
- [ ] 该结论可直接用于月度评审和排期，不只是讨论材料

### ISSUE-06 建立检索质量与索引可观测性基线

- 类型：`AFK`
- 优先级：`P1`
- 目标月份：`2026-07`
- 建议 Owner：知识产品负责人 + Retrieval 负责人
- Blocked by：`ISSUE-04`, `ISSUE-05`

#### Parent

- 路线图目标 B：建立平台治理层
- 工作流 2：知识与报告

#### What to build

为知识与检索链路建立最小可用的指标与可观测性基线，包括索引成功率、重建完成率、检索延迟、结果质量代理指标和失败原因分类。目标不是一次性做完整平台，而是让团队能够判断“知识链路到底是否在稳定支持主流程”。

#### Acceptance criteria

- [ ] 至少定义并落地一组可持续跟踪的知识链路指标
- [ ] 可以按知识库或任务粒度定位索引失败和检索异常
- [ ] 有一版面向运营或技术 owner 的观察口径与阈值建议
- [ ] 月度评审时可以直接引用这些指标而非口头判断

### ISSUE-07 建立报告模板、运行与产物可追踪链路

- 类型：`AFK`
- 优先级：`P1`
- 目标月份：`2026-07`
- 建议 Owner：报告产品负责人 + 报告运行链路负责人
- Blocked by：`ISSUE-03`, `ISSUE-04`

#### Parent

- 路线图目标 B：建立平台治理层
- 工作流 2：知识与报告

#### What to build

让报告模板、模板版本、报告运行、运行输入、知识来源和最终产物之间形成可追踪链路。用户和运营人员都应该能回答“这份报告是由哪版模板、哪条运行、哪些知识输入产出的”，避免报告模块停留在孤立结果页。

#### Acceptance criteria

- [ ] 报告运行记录能看到模板版本、触发上下文和主要输入来源
- [ ] 报告产物能回溯到对应的 report run
- [ ] 模板失效、知识不可用、运行中断等场景的错误语义清晰
- [ ] 至少有一条从模板到产物的端到端验证路径

### ISSUE-08 统一认证、租户与外部依赖错误语义

- 类型：`AFK`
- 优先级：`P1`
- 目标月份：`2026-07`
- 建议 Owner：平台治理负责人 + 认证与租户负责人
- Blocked by：`ISSUE-02`, `ISSUE-05`

#### Parent

- 路线图目标 B：建立平台治理层
- 工作流 3：平台治理

#### What to build

统一认证失败、权限不足、租户配置错误、外部认证服务不可用等场景的错误语义、状态码、日志分类和用户提示。目标是把“失败”区分成可诊断、可恢复、可升级的问题类别，避免把治理层错误继续误报成业务失败。

#### Acceptance criteria

- [ ] 用户能区分无效令牌、无权限、租户配置问题和上游不可用
- [ ] API 状态码与错误码在主要入口保持一致
- [ ] 日志和监控能反映根因，而不是只记录表面异常
- [ ] 常见 401、403、503 场景有回归测试或验收清单

### ISSUE-09 定版平台能力配置模型与治理口径

- 类型：`HITL`
- 优先级：`P0`
- 目标月份：`2026-07`
- 建议 Owner：平台产品负责人 + 集成平台负责人
- Blocked by：`ISSUE-05`

#### Parent

- 路线图目标 B：建立平台治理层
- 工作流 3：平台治理

#### What to build

对模型、Skills、MCP、Connector、Agent 这五类能力给出统一配置模型，明确它们的共同属性、差异属性、发布口径、租户边界和审计要求。该 issue 的目标是先拍板治理模型，再进入后续实现，而不是先堆功能页面。

#### Acceptance criteria

- [ ] 五类能力有统一的配置与发布词汇表
- [ ] 明确哪些字段是全局级，哪些字段是租户级，哪些字段需要审计
- [ ] 明确每类能力的发布、回滚、停用和变更责任
- [ ] 评审结论可直接指导后续配置面和接口实现

### ISSUE-10 交付统一能力配置视图一期

- 类型：`AFK`
- 优先级：`P1`
- 目标月份：`2026-07`
- 建议 Owner：平台产品负责人 + 前后端管理台负责人
- Blocked by：`ISSUE-09`

#### Parent

- 路线图目标 B：建立平台治理层
- 工作流 3：平台治理

#### What to build

基于统一配置模型，交付一版统一能力配置视图一期，让平台配置者不再需要在多个孤立页面或接口之间理解模型、Skills、MCP、Connector、Agent 的关系。该 issue 的重点是治理视图统一，不要求一次性完成所有高级操作。

#### Acceptance criteria

- [ ] 不再需要依赖多套不一致的配置认知来理解平台能力

### ISSUE-11 建立租户级与全局级能力发布边界

- 类型：`AFK`
- 优先级：`P1`
- 目标月份：`2026-07`
- 建议 Owner：平台治理负责人 + 集成平台负责人
- Blocked by：`ISSUE-09`, `ISSUE-10`

#### Parent

- 路线图目标 B：建立平台治理层
- 工作流 3：平台治理

#### What to build

把租户级能力和全局级能力的启用、继承、覆盖、停用和审计路径明确下来。目标是回答“一个能力什么时候是平台共用，什么时候是租户私有，变更后影响谁，谁来回滚”。

#### Acceptance criteria

- [ ] 全局能力与租户能力的边界有明确规则
- [ ] 能力发布、覆盖、停用的影响范围可被解释和追踪
- [ ] 关键变更具备审计记录或等价的追责手段
- [ ] 至少有一条租户启用能力的验证路径

### ISSUE-12 打通报告到闭环工单的结果链

- 类型：`AFK`
- 优先级：`P1`
- 目标月份：`2026-08`
- 建议 Owner：闭环产品负责人 + 工单/状态机负责人
- Blocked by：`ISSUE-07`, `ISSUE-08`

#### Parent

- 路线图目标 A：收敛主产品主线
- 工作流 2：知识与报告
- 工作流 3：平台治理

#### What to build

把报告结果、诊断结论或关键风险项转成闭环工单，并保留回溯关系。该 issue 的目标不是做一个更大的工单系统，而是形成“结果产生 -> 触发处理 -> 状态流转 -> 回看来源”的最小闭环。

#### Acceptance criteria

- [ ] 用户可以从报告或诊断结果创建闭环工单
- [ ] 工单能回溯到触发它的报告结果或诊断上下文
- [ ] 工单状态变化不会丢失来源和处理责任信息
- [ ] 至少有一条从结果到工单再回看的验证路径

### ISSUE-13 完成行业能力边界评审与分层定版

- 类型：`HITL`
- 优先级：`P0`
- 目标月份：`2026-08`
- 建议 Owner：行业解决方案负责人 + 架构负责人
- Blocked by：`ISSUE-05`, `ISSUE-09`

#### Parent

- 路线图目标 C：拆清通用平台与行业层边界
- 工作流 4：行业边界整理

#### What to build

对 InS 认证、组织、设备、行业报表、诊断链路等能力做正式边界评审，明确哪些属于 `Core Platform`，哪些属于 `Enterprise Control Plane`，哪些属于 `Industry Solution Layer`。目标是避免继续把行业能力无边界耦合进通用平台。

#### Acceptance criteria

- [ ] 当前行业相关能力都有明确的层级归属
- [ ] 无法归属或争议较大的能力被列成待决清单
- [ ] 评审结论能直接指导后续目录、发布和 owner 归属
- [ ] 形成一版可供管理层和架构评审使用的分层结论

### ISSUE-14 固化三层产品结构与发布原则

- 类型：`AFK`
- 优先级：`P1`
- 目标月份：`2026-08`
- 建议 Owner：平台产品负责人 + 技术负责人

- 路线图目标 C：拆清通用平台与行业层边界

- [ ] 新增需求可以据此判断应该进入哪一层

### ISSUE-15 决定行业层的交付与发布方式

- 类型：`HITL`
- 优先级：`P1`
- 目标月份：`2026-08`
- 建议 Owner：项目经理 + 行业解决方案负责人 + 技术负责人

- 路线图目标 C：拆清通用平台与行业层边界

#### What to build

对行业层采用“同仓同发、同仓分发、独立方案层管理”中的哪一种方式做出明确决策，并形成对应的协作和发布规则。目标是把分层结论真正落到交付模型，而不是只停留在概念层。

- [ ] 行业层的交付与发布方式有明确决策
- [ ] 决策后的协作方式、变更影响和责任边界被说明清楚
