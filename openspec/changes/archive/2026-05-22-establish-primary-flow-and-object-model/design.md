## Context

DeerFlow 当前处于从多模块独立开发向统一产品主线收敛的关键阶段。各团队在各自上下文中使用相似但不一致的对象模型（如 thread、run、upload、artifact），导致：
- 前后端状态语义不一致，用户无法准确理解"执行中/失败/等待索引"等状态
- 页面间跳转链路不可追踪，从聊天结果找不到对应报告，从报告回不到源对话
- 排期时不同团队对同一概念有不同理解，评审效率低下

本 change 不涉及代码实现，而是一次跨角色共识建立活动。

## Goals / Non-Goals

**Goals:**
- 产出一版被产品、架构、前后端共同认可的第一主流程图
- 产出一版主对象模型清单，每个对象有明确的职责、状态和关系
- 明确工作台一级导航中主入口 vs 扩展域的划分标准
- 识别并隔离所有未决问题，不混入主流程定义

**Non-Goals:**
- 不涉及具体的代码重构或接口变更
- 不解决个别模块的技术债务
- 不覆盖行业层（InS）的特殊对象模型

## Decisions

### 决策 1：采用 Workshop 形式而非文档先行

- **选择**：召集产品负责人、架构负责人、前端和运行时负责人进行 2-3 次集中 Workshop
- **替代方案**：由单一人起草文档后评审 → 容易遗漏视角，来回修改周期长
- **理由**：主流程和对象模型需要多角色同时在场讨论，实时对齐效率远高于异步评审

### 决策 2：主流程图采用"泳道 + 阶段"结构

- **选择**：以"任务/对话 → 工具/知识 → 报告/产物 → 闭环/治理"四个阶段为横轴，以"用户/产品/运行时/网关"为泳道
- **替代方案**：纯线性流程图 → 无法体现不同角色的职责边界
- **理由**：泳道图能同时表达"用户看到什么"和"系统做什么"，适合跨角色对齐

### 决策 3：对象模型采用卡片式清单

- **选择**：每个对象一张卡片，包含：名称、业务含义、生命周期状态、关联对象、归属模块
- **替代方案**：UML 类图 → 过度形式化，不利于非技术角色理解
- **理由**：卡片式清单兼顾技术精度和业务可读性，便于评审和后期维护

## Risks / Trade-offs

- [风险] 关键角色无法同时到场 → Workshop 排期延迟 → 预先征集群时间、设置硬性截止日期
- [风险] 主流程定义过于抽象导致无法指导后续实现 → 在 Workshop 中要求每个阶段至少有一个具体用户场景作为实例
- [风险] 对象模型与现有代码中的模型命名冲突 → 在清单中标注 Legacy Name 对照，不强行改名

## Open Questions

- 是否需要在主流程中显式处理"外部依赖不可用"的路径？
