## Context

当前 `docs/system-capability-matrix.md` 中的 18 个模块的 owner 字段均为"建议角色"（如"工作台产品负责人"），状态和投资结论也标注为"建议"。ISSUE-01 已确认主流程和对象模型基线，ISSUE-05 的下一步是将建议升级为正式决策。

本 change 不涉及代码，是一次纯治理层面的文档升级：将建议版矩阵替换为正式台账。

## Goals / Non-Goals

**Goals:**
- 为能力矩阵中每个模块确定真实的业务 owner 和技术 owner（可以是具体岗位名称或人员姓名）
- 为每个模块标注当前状态（Core / Scale-Up / Stabilize / Incubate）
- 为每个模块标注 Q3 投资结论（继续投入 / 维持 / 缩减 / 停投）
- 将无法定责的模块显式标记为管理风险

**Non-Goals:**
- 不修改代码、API 或系统架构
- 不引入新的管理工具或流程系统
- 不替代现有的组织架构或汇报关系
- 不作为 KPI 考核依据（那是后续 ISSUE-06/09 的范畴）

## Decisions

### 决策 1：台账格式沿用现有矩阵，增加两列

沿用 `system-capability-matrix.md` 的表格结构，新增两列：
- **Q3 投资结论**：`继续投入` / `维持` / `缩减` / `停投`
- **定责状态**：`已确认` / `待确认`

理由：最小变更，不需要新建文档或迁移已有评审材料。

### 决策 2：Owner 从"建议角色"替换为真实信息

两种可接受的填写方式：
- 已知具体负责人：填写姓名
- 已知岗位但不确定人员：填写岗位名称 + 标注 `[待确认人员]`

理由：不伪造未知信息，暴露而非隐藏不确定性。

### 决策 3：无主模块处理规则

任何模块若在评审周期结束前无法确定至少一位 owner，标记为：
- 定责状态：`无主`
- Q3 投资结论：`暂停 — 待定责`
- 列入独立的管理风险清单

理由：ISSUE-05 的验收标准明确要求"仍未定责的模块被显式列为管理风险"。

### 决策 4：投资结论的判断口径

| 结论 | 含义 |
|------|------|
| 继续投入 | Q3 继续分配开发资源，纳入排期 |
| 维持 | 保持现状，仅做必要的维护和 bug 修复 |
| 缩减 | 减少投入，不再新增功能 |
| 停投 | 暂停所有主动开发，仅保留线上运行 |

理由：提供清晰的资源分配信号，避免"都在做、都不清楚优先级"。

## Risks / Trade-offs

- [风险] Owner 确认依赖跨团队协调，可能无法在一个评审周期内完成 → 分批确认，第一批先覆盖 Core 和 Scale-Up 模块
- [风险] 投资结论可能因业务变化而调整 → 台账标注生效日期，月度评审时更新
- [取舍] 不引入独立的 owner 管理系统（如 PagerDuty/ServiceNow）→ 当前规模用文档台账足够，规模扩大后再考虑工具化
