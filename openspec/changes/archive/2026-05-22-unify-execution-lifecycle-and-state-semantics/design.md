## Context

DeerFlow 的核心对象（thread、run、upload、artifact）当前在以下层面各自定义状态：
- 前端 React 组件中通过散落的常量或枚举定义
- 后端 Python/Go 服务中通过各自的 model 定义
- 网关层透传时可能存在语义丢失

这导致同一状态在 API 响应、前端展示和日志中名称不一致，用户和运维都无法准确判断执行情况。ISSUE-01 已定版对象模型，本 change 在此基础上统一状态语义。

## Goals / Non-Goals

**Goals:**
- 定义 thread、run、upload、artifact 的统一状态枚举，前后端共同引用
- 定义统一失败分类（执行失败、上传失败、外部依赖不可用）及每类的用户提示和可恢复动作
- 用户在主链 UI 中可看到失败发生在哪一层
- 关键状态映射有回归测试覆盖

**Non-Goals:**
- 不修改 report run 和 closure ticket 的状态（由 ISSUE-07 和 ISSUE-12 覆盖）
- 不改造日志基础设施，只统一状态口径
- 不涉及状态机的自动化流转逻辑

## Decisions

### 决策 1：状态枚举定义在共享层，前后端引用同一来源

- **选择**：在 API 契约层定义状态枚举（如 OpenAPI/Protobuf），前端和后端各自生成或引用
- **替代方案**：前后端各自定义常量文件手动对齐 → 容易漂移
- **理由**：单一事实来源（SSOT）是避免不一致的唯一手段

### 决策 2：失败分类采用三层结构

- **选择**：失败分为 `EXECUTION_FAILED`（内部执行）| `UPLOAD_FAILED`（上传链路）| `EXTERNAL_DEPENDENCY_UNAVAILABLE`（外部不可用）
- **替代方案**：统一 `FAILED` → 用户无法区分是系统问题还是外部问题
- **理由**：不同失败类型对应不同的用户后续动作（重试 vs 等待 vs 联系管理员）

### 决策 3：每层失败附带 layer 标识

- **选择**：状态对象携带 `failedLayer: "runtime" | "gateway" | "external" | null`
- **替代方案**：通过不同 HTTP 状态码区分 → 只能代表网关层视角
- **理由**：用户需要看到失败发生在运行时、网关还是外部依赖

## Risks / Trade-offs

- [风险] 枚举变更导致线上状态解析失败 → 新增状态向前兼容，废弃状态保留一个版本再移除
- [风险] 前后端发布不同步 → 后端先发新增枚举值，前端后适配展示，保持向后兼容
- [风险] 日志中旧状态名在过渡期与新状态名并存 → 日志查询同时支持新旧两种名称，过渡期后下线旧名
