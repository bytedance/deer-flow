## Context

前端已有完整的 i18n 基础设施（`src/core/i18n/`），支持 en-US 和 zh-CN 两种语言，通过 React Context 提供 `useI18n()` hook，包含类型安全的翻译键定义（约 740 个键）。Cookie 持久化用户语言偏好，自动检测浏览器语言。

核心工作台组件（侧边栏、输入框、设置页、Agents 页）已正确接入 i18n。但报告模板/运行页面（Sprint C 新增功能）和 GenUI 组件（设备选择器、Markdown 编辑器等）绕过了 i18n 系统，直接硬编码中文字符串。

## Goals / Non-Goals

**Goals:**
- 补全翻译键定义，覆盖报告模板页面、报告运行页面、GenUI 组件中的所有用户可见字符串
- 将所有硬编码中文字符串替换为 `t.xxx` 调用
- 确保 en-US 和 zh-CN 翻译完整且准确
- 保持类型安全——新增键必须在 `types.ts` 中定义

**Non-Goals:**
- 不新增语言支持（仅维护 en-US 和 zh-CN）
- 不修改后端 i18n（后端继续使用错误码 → 前端本地化模式）
- 不重构 i18n 基础设施本身
- 不处理 `ui/` 和 `ai-elements/` 中的字符串（这些是自动生成的注册表组件，不应手动编辑）

## Decisions

### 1. 翻译键组织结构

**决策**：按组件/功能域分组新增键，复用现有的顶级命名空间。

- 报告模板相关键归入 `marketplace` 和 `editor` 现有命名空间（这两个命名空间已存在相关键）
- 报告运行相关键归入新增的 `reportRuns` 命名空间
- GenUI 组件键归入新增的 `genui` 命名空间

**理由**：避免创建过于细碎的命名空间，同时保持与现有结构一致。`genui` 作为新的顶级命名空间可以容纳所有 GenUI 块的通用字符串。

### 2. 组件改造方式

**决策**：在每个需要 i18n 的组件顶部调用 `useI18n()`，将硬编码字符串逐一替换为 `t.xxx` 引用。

**理由**：这是项目中已有的标准模式，与核心组件保持一致。不需要引入新的抽象层。

### 3. 设备类型名称的翻译

**决策**：设备类型名称（旋转机组、机泵、静设备、往复机组）作为翻译键处理，而非从后端数据动态获取。

**理由**：这些是 UI 固定的设备分类标签，不是动态数据。作为翻译键处理可以保证类型安全和双语一致性。

**替代方案**：从后端 API 返回设备类型名称——但这些是前端 GenUI 组件的固定 UI 标签，后端不控制前端显示文本。

## Risks / Trade-offs

- **翻译键膨胀** → 新增约 80 个键，但都在明确的命名空间下，可维护性可控
- **E2E 测试断言漂移** → 如果 E2E 测试中有硬编码中文字符串断言，需要同步更新。通过 grep 排查并修改。
- **遗漏硬编码字符串** → 通过全局搜索中文字符（`[一-鿿]`）交叉验证，确保不遗漏
