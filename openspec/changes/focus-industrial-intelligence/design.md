## Context

当前产品（DeerFlow）的工作台中同时承载了两类 skills：通用型（deep-research、data-analysis、image-generation）和工业专用型（vibration-fault-diagnosis、ins-device-analysis、rotating-diagnosis-*、monitoring-*）。产品的主流程（对话 → 工具/知识 → 报告 → 闭环）虽然已经定义，但没有明确区分服务对象。现有 `interaction-mode-tiers` 和 `result-presentation-tiers` 定义了 Basic/Pro/Ultra 三层交互和展示，但各层对工业场景和通用场景一视同仁，没有优先级区分。

约束条件：
- 通用 skills 仍有用户基础，不能直接删除
- 工业 skills 依赖后端特定的数据管道（Nacos 服务发现、Java RPC 客户端、PG 存储），架构成本已经投入
- 前端工作台的技能选择器、首页推荐、导航菜单需要同步调整

## Goals / Non-Goals

**Goals:**
- 建立 skills 分层模型（核心工业层 / 基础能力包），支持按层过滤和展示
- 重构前端入口和推荐逻辑，工业场景优先展示
- 为首次使用工业场景的用户提供专属引导流程
- 产品定位从"通用 AI 助手"调整为"工业智能平台"，体现在品牌、入口、文档
- 保持通用 skills 可用但降级为基础工具

**Non-Goals:**
- 不删除任何通用 skills，仅调整展示优先级
- 不重构后端工业数据管道（已在其他 change 中覆盖）
- 不引入新的订阅/付费模型（定价策略不在此次范围）
- 不改变现有 Basic/Pro/Ultra 三层技术架构，仅调整各层的默认推荐内容

## Decisions

### Decision 1：Skills 分层采用标签模型而非独立注册表

**选择**：在现有 skill 注册表中为每个 skill 增加 `tier` 标签（`core-industrial` / `foundation`），而非拆分为两个独立的 skill 注册表。

**理由**：
- 标签模型对现有架构侵入最小，不需要新的存储或 API 端点
- 技能列表接口只需返回额外字段，客户端按 tier 过滤即可
- 未来如需新增层级（如 `partner` 第三方技能），只需扩展枚举值

**替代方案**：拆分为两个独立的 skill registry 服务。否决原因：引入不必要的服务边界，增加运维复杂度，且通用 skills 和工业 skills 共享相同的运行时基础设施。

### Decision 2：前端展示采用"工业优先 Tab + 通用折叠"模式

**选择**：技能选择器默认展示工业 skills Tab，通用 skills 放在"基础工具"折叠区域。首页推荐卡片优先展示工业场景（设备诊断、监测分析、趋势报告）。

**理由**：
- 用户首次接触产品时立即感知工业智能定位
- 通用 skills 仍然可达，但需要主动展开，减少视觉干扰
- 与现有技能选择器组件兼容，只需调整排序和分组逻辑

**替代方案**：完全隐藏通用 skills，仅在搜索中可达。否决原因：现有通用 skills 仍有用户基础，完全隐藏会引发用户投诉。

### Decision 3：工业引导流程作为可选 Overlay，不阻塞主流程

**选择**：首次进入工作台的工业用户触发引导 Overlay（3-5 步），引导用户完成一次设备诊断或监测分析。引导可跳过，不影响后续使用。

**理由**：
- 强制引导会降低高级用户的效率
- Overlay 模式与现有 A2UI 组件体系兼容
- 引导完成后在用户偏好中标记，避免重复展示

**替代方案**：强制引导流程，必须完成才能使用产品。否决原因：与现有 `primary-flow-definition` 中"对话/任务即入口"的原则冲突。

### Decision 4：主流程定义增加"工业场景优先"约束

**选择**：在 `primary-flow-definition` 中增加约束——主流程的默认示例、文档、推荐路径均优先使用工业场景。通用场景作为"也支持"的补充说明。

**理由**：
- 主流程定义是产品和开发的权威参考，在此层面确立工业优先具有全局影响
- 不改变主流程的技术架构，仅调整默认内容和推荐逻辑

## Risks / Trade-offs

**[通用用户流失风险]** → 通过保留通用 skills 可达性（折叠而非隐藏）和基础能力包的品牌包装来缓解。如果通用用户占比超过 40%，需重新评估分层策略。

**[工业引导流程与现有 onboarding 冲突]** → 引导流程检测用户是否已完成过工业场景操作，如已完成则不展示。与现有引导系统（如有）通过事件总线协调。

**[前端重构工作量]** → 技能选择器、首页推荐、导航菜单的改造预计需要 2-3 个 sprint。采用渐进式发布：先上线 tier 标签和 API，再逐步调整前端展示。

**[团队认知转变阻力]** → 需要在产品周会上正式宣布"工业优先"原则，并在需求评审 checklist 中增加"是否服务工业场景"的检查项。

## Migration Plan

1. **Phase 1（Sprint 1）**：后端增加 tier 标签，API 返回 tier 信息，数据库 migration 为现有 skills 打标签
2. **Phase 2（Sprint 2）**：前端技能选择器重构，工业 skills 前置展示
3. **Phase 3（Sprint 3）**：首页推荐和导航重构，工业引导流程上线
4. **Phase 4（Sprint 4）**：文档和品牌材料更新，内部宣导

回滚策略：每个 Phase 独立可回滚。如果工业优先策略引发严重用户反馈，可通过配置开关快速恢复通用优先的展示模式。

## Open Questions

- 工业用户识别：是否需要用户注册时选择行业/角色，还是通过行为数据自动识别？
- 通用 skills 的品牌包装：是否统一命名为"基础能力包"并设计独立 logo？
- 指标衡量：如何定义"工业优先"成功指标——工业 skills 使用量占比？工业用户留存率？
