# 模块二 · Agent 驱动的智能报表工厂

> 所属提案：智能问数 · 创新提案
> 本章定位：智能问数体系中"数据 → 决策材料"的关键输出形态
> 核心特征：**一座由 Agent 调度运行的报表工厂**

---

## 一、模块定位：把"做报表"变成一座 Agent 调度的工厂

智能问数的目标，是让业务人员用自然语言就能拿到想要的数。但"拿到数"和"用好数"之间，还有一段距离——大多数决策场景下，决策者真正需要的不是一组数字，而是一份**结构清晰、数据准确、口径可查、可直接送达的报表**。

本模块要交付的，正是一座**由 Agent 调度运行的报表工厂**：

- **智能问数解决"问到数据"**——把自然语言变成结构化查询；
- **智能报表工厂解决"把数据做成决策材料"**——把零散数据，按模板、按工序、按规范，组织成可读、可审、可发的正式报表。

**关键差异：这座工厂的"总指挥"，是一个 Agent。**

它不是"另一个 BI 工具"——传统 BI 把人放在操作员位置，所有配置、运行、调试都要人来点；它也不是"无人值守的全自动机器"——全自动意味着失控风险。它是一座**有 Agent 调度、有关卡把关、有产品交付**的工厂：Agent 调度工序，工序产出品，品检留痕，请示还人。

---

## 二、业务现状：报表这件事，长期被三件事困扰

很多组织做报表，长期绕不开三个痛点：

1. **慢**——从拉数据到排版到送审，一个流程走下来少则半天、多则数日。
2. **乱**——过程中谁改过什么、用什么口径、哪里出错，靠人脑记忆，事后追溯困难。
3. **险**——一个环节出错，整张表作废，重头再来；中间没有"停下来确认"的机制，问题常常被掩盖到最后一刻才暴露。

更深一层：**这件事高度依赖"熟手"**。一个老员工离职，他脑子里那套"模板怎么调、数据在哪取、领导喜欢什么风格"的隐性知识就带走了。新人接手，要么培训半年，要么报表质量断崖式下跌。

## 三、工厂设计：Agent 总指挥 + 工序标准化

### 工厂里的三类角色

| 角色 | 担任者 | 职责 | 特点 |
|---|---|---|---|
| **总指挥** | Agent | 感知需求、调度工序、把关决策 | 看得见全局，能在节点间调度 |
| **机械工人** | 确定程序 | 模板体检、数据搬运、表格拼合、图表生成 | 跑得稳、可重放、可单测 |
| **创意工匠** | 极少数环节 | 写计算脚本、写描述文案 | 真正需要"动脑"的地方 |

**总指挥不亲自干活**——它调度机械工人跑工序、在关键节点叫停请示、把结果交给创意工匠加工、再调度机械工人包装成品。它的价值在于"让整个工厂有序运转"，而不是"自己样样精通"。

### 工序链：准备 → 判断 → 包装

**第一段 · 数据准备（5 个机械化工序）**
模板体检 → 结构拆解 → 数据查询 → 表格拼合 → 公式提取
由机械工人执行，Agent 监督调度。

**第二段 · 判断处理（2 个需要"动脑子"的工序）**
写计算脚本 → 写描述文案
由创意工匠承担，是整条流水线中最小化的"判断力使用"。

**第三段 · 成品包装（4 个机械化工序）**
验算结果 → 回填计算 → 配置图表 → 输出文档
回到机械工人，把判断环节的产物装到最终文档里。

### 三个"请示关卡"：Agent 把决策权显式交还给人

- 模板体检完之后
- 数据取完之后
- 描述生成完之后

Agent 在这三个节点**主动停下**，把"继续 / 停下"的决定权显式交回给负责的领导。这不是技术设计，是**风险设计**：让流程在不确定的地方显式地停下来，而不是默默继续。

---

## 四、为什么是 Agent 驱动，而不是"传统 BI"或"全自动"

四个底层判断：

### 1. 工序多、节点多、角色多，需要一个"看得见全局"的调度者

一条报表生产线有十余个节点、若干角色。靠人盯，盯不过来；靠纯程序，又处理不了"这里要不要请示""那边卡住了怎么绕"这类需要判断的环节。Agent 正好填补这个位置——它既能跑流程，又能做局部判断，还能把判断不了的事显式升级给人。

### 2. 决策点必须显式化，这是 Agent 最擅长的事

传统 BI 把决策藏在用户的鼠标点击里——点错了就错到底。本模块里，Agent 把每一个关键决策点**显式暴露给负责的领导**：模板体检后、数据取完后、描述生成后。它不是替代人决策，而是**让决策可见**。

### 3. 异常处理需要灵活性，但不能失去可控性

全自动系统遇到异常，要么崩、要么默默重试、要么伪装成功。本模块里，Agent 看到异常时**打上标记、把问题摆出来**，让领导决定如何处理。灵活但不失控。

### 4. 沉淀的过程知识，需要有人"读懂并运用"

工厂运行久了，会积累大量中间产物、模板、计算脚本、描述文案。这些沉淀不是死档——Agent 能在下一次任务中**读懂并运用**它们：识别"这是上月报模板""这是领导偏好的描述风格"，把过去的知识转化为当下的效率。

## 五、给组织带来的变化

| 维度 | 过去 | 现在 |
|---|---|---|
| **效率** | 半天到一天 | 小时级 |
| **质量** | 依赖个人能力 | 模板与工序标准化，能力下沉 |
| **风险** | 错误被掩盖到最后 | Agent 主动请示，关卡把决策点显性化 |
| **追溯** | 靠人脑记忆 | 中间产物全留痕，随时可查 |
| **人才** | 高度依赖熟手 | 新人按模板即可产出合格结果 |
| **知识** | 留在员工脑子里 | Agent 读懂并复用，沉淀为长期资产 |
| **角色重塑** | 人是操作员 | 人是决策者，Agent 是调度员 |

---

## 六、它到底"创新"在哪里

不是"用了 AI"，而是**一套做事方式的重新设计**：

- **Agent 调度 + 工序标准化**——Agent 不替代人做判断，而是把人从操作员位置上解放出来；
- **机械化和判断力严格分工**——把容易跑稳的交给程序，把需要动脑的留给判断；
- **决策权显式回到人手里**——三个请示关卡，由 Agent 主动叫停；
- **失败可见、部分可用**——一格坏了不毁整张表，问题摆到桌面上处理；
- **过程即资产**——每一份报表的中间产物都沉淀下来，Agent 在下一次任务中读懂并复用。

---

## 七、与传统方式的差异化对比

| 维度 | 传统 BI 报表工具 | 模板 + 人工搬运 | 智能问数 · Agent 驱动的报表工厂 |
|---|---|---|---|
| **调度方式** | 人点击 / 配置 | 人手工搬运 | **Agent 调度工序链** |
| **数据获取** | 人工写 SQL | 人工导出 + Excel 拼合 | 与问数模块打通，自动取数 |
| **格式排版** | 拖拽式设计器 | 手工调整 | 模板标准化，自动回填 |
| **错误处理** | 报错即崩 / 静默失败 | 全凭个人经验 | **Agent 主动标记 + 请示决策** |
| **过程留痕** | 几乎不留 | 完全靠人脑 | 全流程中间产物落盘 |
| **能力门槛** | 需培训 BI 工具 | 需培训 Excel + 业务 | 按模板即可，能力下沉 |
| **角色定位** | 人是操作员 | 人是工人 | **人是决策者，Agent 是调度员** |

## 八、风控与边界

为保证工厂的可控性，模块内设置以下硬性边界：

- **原始模板只读**——用户上传的样张不可被 Agent 或后台程序自动修改。
- **生成程序只读**——工厂自身的脚本不可被后台改动，所有变更走代码评审流程。
- **Agent 越权禁止**——Agent 仅在"调度、请示、标记"范围内行事，不得擅自修改原始材料，不得擅自做出需要领导决策的判断。
- **决策权显式化**——三个请示关卡强制暂停，等待负责领导确认后再继续。
- **失败显性化**——单格失败用标记呈现，不掩盖、不假装。
- **过程全留痕**——所有中间产物落盘，事后可审计、可回放、可供 Agent 复用。

## 九、落地节奏

建议分三步走：

1. **试点一个高频报表场景**（如月报、季报）——验证 Agent 调度工序链是否跑通、请示关卡是否符合实际决策习惯。
2. **沉淀一批标准模板**——把"什么算合格报表"这件事模板化、显性化，让模板成为组织的资产而不是个人的手艺。
3. **推广到更多场景 + 培养"工序运维"角色**——既懂业务又懂模板调优的人，是 Agent 与工厂长期高效协作的关键。

## 十、给评审组的总结

> **本模块交付的，是一座由 Agent 调度的智能报表工厂。**
>
> 它不是"用 AI 做报表"，也不是"无人值守的全自动系统"。它的核心创新在于：
>
> **把"做报表"这件原本靠人盯、靠熟手、靠运气的事，变成一座按工序走、按节点把关、按产物留痕、按 Agent 调度的工厂。**
>
> 在这座工厂里：
> - **机械工人**负责稳定执行（90% 的工序）
> - **创意工匠**负责少数需要动脑的环节（2 个工序）
> - **Agent 总指挥**负责调度、把关、把决策权交回人
> - **领导**从操作员位置上解放出来，回到真正的决策者角色
>
> 这是组织能力的升级，是"做事方式"的升级，不是某一项工具的升级。
