# Search query benchmark

Measures how closely DeerFlow's **first generated `web_search` query** matches human queries for the same information need Given a backstory, does the agent produce a query that keeps the topic, entities and constraints? It runs through the production Gateway and stops before the first search executes, so you can compare query formulation before and after a change without paying for a full search-and-answer evaluation. Query formulation determines which information the search engine is asked to find, so losing an entity, a location or a constraint at this step can send the rest of a research task in the wrong direction.

Each backstory is compared against several human reference queries. See the [glossary](GLOSSARY.md) for terms.

## What is measured

We measured and evaluate three things:

- **Meaning alignment:** semantic similarity between the generated query andeach human reference, averaged within a backstory.
- **Word overlap:** lexical similarity with the references, which helps expose changes in wording and missing shared terms.

Direct answers, `decision_limit` and errors are reported as unscored outcomes, never as zeros.

> **These are proxies for agreement with human queries.** They do not measure retrieval relevance, Recall@k, nDCG, answer correctness, latency or cost yet.

## Relevant research

These papers motivate the benchmark creation, dataset, measurements and optimization ideas. This benchmark does not reproduce their retrieval experiments or reported gains.

## Quick start

Commands are **Bash**, run from the repo root (on Windows use Git Bash or WSL). Requires Python 3.12+, uv and the prerequisites in [CONTRIBUTING.md](../../../../CONTRIBUTING.md).

### 1. Start the Gateway (terminal 1)

```sh
make config            # first checkout only
cd backend && uv sync --locked

mkdir -p scripts/benchmark/search_query/runs/snapshots
cp ../config.yaml scripts/benchmark/search_query/runs/snapshots/baseline.yaml

export DEER_FLOW_CONFIG_PATH="$(uv run --no-sync python -c "from pathlib import Path; print(Path('scripts/benchmark/search_query/runs/snapshots/baseline.yaml').resolve())")"
export DEER_FLOW_HOME="$(uv run --no-sync python -c "from pathlib import Path; print(Path('scripts/benchmark/search_query/runs/runtime-baseline').resolve())")"
make gateway
```

Requirements for a valid comparison:

- A reachable model with credentials, and an agent exposing `web_search` with a string `query` argument ([configuration guide](../../../docs/CONFIGURATION.md)).
- Identical tools, skills, memory and sampling settings across runs, unless one is the variable under test.
- A dedicated runtime home, and evolving memory isolated or disabled. Each case creates a fresh thread, and subagents are disabled.
### 2. Run the benchmark (terminal 2, from `backend/`)

```sh
export DEERFLOW_BENCHMARK_URL=http://127.0.0.1:8001/api
BENCH=scripts/benchmark/search_query
GATEWAY_REVISION=YOUR_DEPLOYED_COMMIT_OR_IMAGE_DIGEST   # e.g. `git rev-parse HEAD`

benchmark() {
  uv run --no-sync --with sentence-transformers==5.1.2 \
    python scripts/benchmark/search_query/run.py "$@"
}

# Smoke test first, and check the outcome (exit code 0 can still mean an unscored case)
benchmark --gateway-revision "$GATEWAY_REVISION" \
  --runtime-artifact "config=$BENCH/runs/snapshots/baseline.yaml" \
  --limit 1 --output-dir "$BENCH/runs/baseline-smoke"

# Full baseline
benchmark --gateway-revision "$GATEWAY_REVISION" \
  --runtime-artifact "config=$BENCH/runs/snapshots/baseline.yaml" \
  --output-dir "$BENCH/runs/baseline"
```

Notes:

- **Auth:** for an authenticated Gateway, set `DEERFLOW_BENCHMARK_TOKEN` to a personal access token with `threads:write`, `runs:create` and `runs:read`. Without `DEERFLOW_BENCHMARK_URL`, the runner uses `http://127.0.0.1:2026/api` (nginx).
- **Options:** `--limit N` runs only the first N cases (not a random sample). `--model NAME` selects a configured DeerFlow model *name* (not the provider ID). `--max-decisions N` sets the checkpoint budget (default 8); keep it fixed across comparisons. Each `--output-dir` must be new.
- First run downloads and caches the pinned encoder. After that, embeddings run offline, but the Gateway model and any preparatory tools must stay reachable.
### 3. How to Evaluate

To measure a change, run the benchmark twice with everything else identical, then compare the two sets of scores:

1. **Before the optimization:** the baseline run from step 2 (no change applied).
2. **After the optimization:** apply your change, restart the Gateway, and run the benchmark again as the candidate.
3. **Compare:** calculate both runs' scores and their paired difference in [step 4](#4-compare).
Start by inspecting low-similarity and no-search baseline cases and writing a testable hypothesis (e.g. "preserving locations reduces topic drift"). Then apply the optimization by creating the candidate configuration and restarting the Gateway with it and a fresh runtime home seeded with the same initial state:

```sh
cp "$BENCH/runs/snapshots/baseline.yaml" "$BENCH/runs/snapshots/candidate.yaml"
```

Example prompt candidate (merge into any existing `lead_prompt_overlay`; see [prompt overlays](../../../docs/CONFIGURATION.md#prompt-overlays)):

```yaml
lead_prompt_overlay:
  append: |
    When forming a web search query, identify the user's information need.
    Preserve named entities, locations and explicit constraints.
    Remove narrative filler and avoid adding unsupported assumptions.
    Express the need as a focused query suitable for a search engine.
```

Few-shot examples must come from separate data. Never put evaluation references in the agent's context.

```sh
# In terminal 1: Ctrl+C, then
export DEER_FLOW_CONFIG_PATH="$(uv run --no-sync python -c "from pathlib import Path; print(Path('scripts/benchmark/search_query/runs/snapshots/candidate.yaml').resolve())")"
export DEER_FLOW_HOME="$(uv run --no-sync python -c "from pathlib import Path; print(Path('scripts/benchmark/search_query/runs/runtime-candidate').resolve())")"
make gateway

# In terminal 2
benchmark --gateway-revision "$GATEWAY_REVISION" \
  --runtime-artifact "config=$BENCH/runs/snapshots/candidate.yaml" \
  --output-dir "$BENCH/runs/candidate"
```

Once the candidate run finishes, you have a baseline and a candidate result to compare.

Other optimizations you can evaluate this way: a different model or checkpoint, sampling parameters, a skill, tool-description changes, or query rewriting/expansion/reranking **before** the first `web_search` is emitted. Update `GATEWAY_REVISION` if server code changed, and retain a diff for uncommitted changes.

**Out of scope:** rewriting inside the search provider, later queries, document reranking and subagent-only changes all happen after the breakpoint and are not measured.

### 4. Compare

`summary.json` has outcome counts and coverage but **not** overall means. Compute them from `results.csv`:

```sh
uv run --no-sync python - "$BENCH/runs/baseline" "$BENCH/runs/candidate" <<'PY'
import csv, json, sys
from pathlib import Path
from statistics import fmean

metrics = ("semantic_mean", "lexical_jaccard_mean")
runs = []
for directory in map(Path, sys.argv[1:]):
    with (directory / "results.csv").open(encoding="utf-8", newline="") as f:
        rows = {r["case_id"]: r for r in csv.DictReader(f)}
    scored = {k: r for k, r in rows.items() if r["outcome"] == "scored"}
    summary = json.loads((directory / "summary.json").read_text(encoding="utf-8"))
    means = {m: fmean(float(r[m]) for r in scored.values()) if scored else None
             for m in metrics}
    print(directory.name, "coverage:", summary["coverage"],
          "outcomes:", summary["outcomes"], "scored means:", means)
    runs.append((rows, scored))
if runs[0][0].keys() != runs[1][0].keys():
    raise SystemExit("Compare runs with identical case IDs")
common = sorted(runs[0][1].keys() & runs[1][1].keys())
print("Cases scored in both runs:", len(common))
for m in metrics:
    d = [float(runs[1][1][k][m]) - float(runs[0][1][k][m]) for k in common]
    print(m, "paired mean delta:", fmean(d) if d else None)
PY
```

Before interpreting:

- Confirm matching intended settings in `configuration.json`.
- Read the largest regressions, not just the means. Report coverage and all outcomes alongside similarity, since a higher mean on fewer, easier cases can hide regressions.
- Keep the encoder, reference weighting, case order and budget fixed. Repeat runs in new directories to estimate stochastic spread; one small delta is not conclusive. There is no built-in pass/fail threshold.
- For a chosen candidate, measure retrieval relevance and downstream answer quality (and latency/cost if relevant) separately.
## How capture works

Only the original backstory enters a fresh thread. The runner pauses the lead agent before its tools node:

- A batch of only preparatory tools is resumed on the same thread (those tools **do** execute, and their output may vary).
- At the first batch containing `web_search`, the runner takes the first search call in checkpoint order. **Nothing in that batch executes.**
- A direct answer ends the case. A malformed batch or search call is an error. Exhausting `--max-decisions` gives `decision_limit`.
Unscored outcomes (direct answer, `decision_limit`) are valid and leave metric cells empty. The exit code is nonzero only for setup failures or case errors.

## Provenance

`--gateway-revision` is an operator assertion identifying the running server; the runner's Git revision does not. Repeat `--runtime-artifact NAME=PATH` for each snapshot you retain (config, prompt overlays, skill manifests, memory). Their SHA-256 hashes are recorded without copying secrets. Files must not change during a run, or the command fails and the run is discarded. For a remote Gateway, use exported snapshots, and keep the originals since a hash cannot restore them.

The Gateway's assembly fingerprints are keyed per process, so they cannot prove equality across restarts or workers; use the retained artifacts for cross-deployment comparisons. They also do not capture the rendered system prompt or arbitrary provider kwargs and retry settings, so keep those in your snapshots. Recorded evidence supports reproducible setup but does not make model calls or live tool results deterministic.

## Output files

Each run writes to a new ignored directory under `runs/` (or `--output-dir`). Treat `runtime-*.json` as private.

| File | Contents |
| --- | --- |
| `results.csv` | Case ID, backstory, human queries (JSON list), reference count, captured query, outcome, two metric means, effective model, thread ID, decision count, error diagnostic |
| `summary.json` | Outcome counts, coverage, runner/encoder revisions |
| `configuration.json` | Capture policy, budget, requested model/context, client timeout/retries, runner/encoder revisions, artifact hashes, Gateway revision |
| `runtime-NNNN.json` | Thread and run IDs, host assembly evidence (effective model, sampling, fingerprints), checkpoint digest, injected context messages |

A case fails if host evidence is missing or cannot be tied to exactly one run.
