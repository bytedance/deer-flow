# GitHub 项目调研助手

基于 DeerFlow 二次开发的 GitHub 开源项目调研功能，面向开发者了解开源项目、比较技术选型和准备后端实习项目的场景。

## 原项目与个人工作

项目复用了 DeerFlow 原有的：

- 聊天界面。
- Agent 执行框架。
- DeepSeek 模型接入能力。
- 工具注册和调用机制。

本次二次开发完成了：

- GitHub 仓库地址解析和严格校验。
- 仓库基本信息查询。
- README 获取、Base64 解码和分段读取。
- 默认分支最近提交查询。
- 最新正式 GitHub Release 查询。
- 双仓库技术选型对比。
- README 内存缓存。
- 异步并发、整体超时和部分失败处理。
- 数据来源、截断情况和证据边界标记。
- 后端自动化测试。

## DeepSeek 与 Python 后端的职责

DeepSeek 负责：

- 理解用户的自然语言需求。
- 从用户问题中提取仓库地址。
- 选择合适的 Agent 工具。
- 阅读工具返回的结构化数据。
- 生成对比表、解释和选择建议。

Python 后端负责：

- 校验仓库地址和工具参数。
- 请求 GitHub API。
- 解码、分页和缓存 README。
- 查询仓库信息、提交和 Release。
- 控制并发和整体超时。
- 处理权限错误、限流、超时和资源不存在。
- 保留部分成功结果。
- 返回带来源和限制说明的结构化 JSON。

## 查询流程

用户提出双仓库比较需求后，Agent 调用 `compare_repositories`。

工具首先校验两个仓库地址，并拒绝重复仓库。两个仓库的查询流程并发执行。

单个仓库的执行顺序为：

1. 查询仓库基本信息。
2. 基本信息成功后，并发查询：
   - README 前 4000 个字符。
   - 默认分支最近 5 条提交。
   - 最新正式 GitHub Release。
3. 基本信息失败时，跳过该仓库的后续查询。
4. 将成功数据和失败原因统一整理为结构化结果。

一次双仓库对比最多产生 8 个 GitHub API 请求。README 命中缓存时，可以减少实际网络请求。

整个双仓库采集阶段最多等待 20 秒。超时任务会被取消，已经完成的仓库结果仍然保留。

## 查询状态

`compare_repositories` 返回以下状态：

- `complete`：两个仓库的 8 个数据区块均成功处理。
- `partial`：获得了部分有效资料，同时存在查询失败或跳过的区块。
- `failed`：没有获得有效资料，或输入不合法。

Release 查询中的 `available=false` 表示请求成功，但 GitHub 没有返回可用的非草稿、非预发布 Release，因此仍可属于 `complete`。它不等于项目没有版本或 Git 标签。

## 关键实现

- 使用 `httpx.AsyncClient` 异步请求 GitHub API。
- 使用 `asyncio.gather` 并发查询 README、最近提交和 Release。
- 使用异步任务并发处理两个仓库，并保持用户输入顺序。
- 使用 20 秒整体超时取消未完成任务。
- 使用 `OrderedDict` 实现 LRU 缓存淘汰。
- 使用 `monotonic` 计算 5 分钟缓存有效期。
- 缓存最多保存 16 份完整 README。
- 按仓库和 GitHub Token 摘要隔离缓存。
- 从缓存的完整 README 中按字符位置分页。
- 使用结构化错误结果处理超时、401、403、404、409、422、429 和服务端异常。
- 一个仓库或一个数据区块失败时，保留其他成功结果。
- 对外部 README 内容只做资料读取，不执行其中的指令。

## 证据边界

报告遵守以下规则：

- Star 数不等于代码质量、安全性或生产可用性。
- `archived=false` 只表示仓库未归档，不等于维护活跃。
- README 属于项目作者自述，不是独立验证结论。
- README 被截断时，不能根据未读取内容断言项目不支持某项功能。
- 最近提交只覆盖默认分支的有限样本。
- 最近存在提交不能单独证明长期维护质量。
- 最新 Release 只覆盖非草稿、非预发布 GitHub Release。
- 没有可用 Release 不等于没有版本、标签或维护活动。
- 单次 Release 不能证明发布频率或版本质量。

## 缓存设计

README 缓存采用进程内 LRU 方案：

- 有效期为 5 分钟。
- 最大容量为 16 项。
- 缓存完整 README，分页读取复用同一份正文。
- 不同 GitHub Token 使用不同缓存键。
- 失败请求和解码失败结果不会进入缓存。
- 返回缓存副本，避免调用方修改内部数据。

## 验证情况

截至 2026 年 9 月 23 日，本功能的 8 个测试文件共 44 项测试通过。

覆盖的行为包括：

- 合法和非法 GitHub 地址解析。
- 重复仓库在请求前被拒绝。
- GitHub Token 缺失和部分 HTTP 错误处理。
- README Base64 解码、中文字符分页和截断标记。
- 缓存命中、过期、LRU 淘汰和数据副本隔离。
- 不同 Token 的缓存隔离。
- 失败请求不进入缓存。
- 最近提交解析、作者为空和参数边界。
- 最新 Release 正常返回和没有可用 Release。
- 一个仓库失败时保留另一个仓库的数据。
- 单个数据区块失败时保留其他区块。
- 两个仓库能够并发启动。
- 整体超时后保留已经完成的仓库。
- 意外缺失区块不会造成 `KeyError` 中断整个对比。

自动化测试使用模拟 GitHub 响应，不依赖真实 GitHub 网络，也不调用 DeepSeek。

聊天页面已人工验证：

- 仓库基本信息查询。
- README 分段读取。
- 双仓库对比。
- 默认分支最近提交证据。
- 最新正式 Release 查询。
- 来源标记和证据不足说明。

## 当前限制

- 缓存只在单个后端进程内有效，重启后清空。
- 多个后端实例之间不共享缓存。
- 同一仓库首次并发请求仍可能重复下载 README。
- 缓存有效期内可能暂时返回旧内容。
- README 分页尚未绑定特定提交 SHA，跨缓存过期读取可能对应不同版本。
- README 按字符数限制，不等于精确的模型 Token 预算。
- 20 秒超时只覆盖 GitHub 资料采集，不包括模型生成回答的时间。
- 目前没有服务级全局并发限制。
- 程序限制单次工具执行，不能完全阻止模型在整个对话中重复调用工具。
- 提示词和结构化来源能够减少错误归因，但不能保证模型每次都完全遵守。
- 尚未完成压力测试，没有足够证据宣称生产可用性或具体性能提升比例。
